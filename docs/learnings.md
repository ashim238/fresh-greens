## fix/en-route-defects (2026-05-10)

Two real defects landed on /en-route that didn't get caught before because they only manifest at specific times of day or with seeded report density. Worth keeping the post-mortems together — both are about parity drift between /home and /en-route, where features added on /home don't automatically follow on /en-route.

- **`SunCalc.getTimes(date, lat, lng)` returns events for the calendar day passed in, not the next sunrise/sunset.** A 1 AM segment computes against today's 7:30 PM sunset and reports +1110 minutes — which the band table reads as full daylight (orange/yellow), not night. `gradientSegments` had this bug since the daylight gradient shipped, but it only surfaces between midnight and sunrise — a window most testing doesn't hit unless you're explicitly trying. Fixed by checking `segmentTime < sunTimes.sunrise` and forcing `minutesToSunset = -1` when pre-dawn, which routes through the existing "negative → night" band. Worth keeping: solar-time math has a hidden assumption that "now" is during the daylight portion of the day passed in; pre-dawn and post-midnight are both edge cases that need explicit handling.
- **Marker clustering on /home didn't auto-apply to /en-route.** /home got `clusterPointZones` + `mapRegion`/`mapSize` state in `feat/community-report-mechanic`; /en-route renders the same `reportZones` but never picked up the clustering wiring, so dense seed data in Mobile, AL stacked four LandmarkMarkers on top of the user-location dot at the default zoom (17 / 1000m altitude). The pure function in `lib/clustering.ts` is reusable; the wiring isn't. Worth keeping: when a feature ships on /home, audit /en-route for the same render path. The two screens share the data pipeline (zones, reports, scoring) but each owns its own render — features don't cascade. A "render-path parity" check belongs in the next Figma fidelity audit's checklist.

## feat/schedule-for-am (2026-05-09)

Replaced the static "Schedule for later" chip on /home with a real computation: `suggestedDepartureForDaylight(route, now)` in `lib/daylight.ts` returns a departure time only when leaving later genuinely buys more daylight, otherwise `null`. v1 rule: pre-sunrise departures get sunrise+15min (small buffer past the horizon — visually past the dim band, though still inside scoring.ts's dawn ±30-min wildlife window), capped to a 3-hour look-ahead with a 5-minute floor. The chip — and its rationale copy ("Heads up! You can leave in a bit…") — both gate on the suggestion existing, so mid-day departures hide instead of showing a meaningless time.

- **A "schedule for X" suggestion has to be explicitly nullable, not a default copy.** First instinct was to always render the chip with computed text, falling back to "Schedule for later" if the math didn't yield anything. That's what the static version was doing. But the rationale copy ("you can leave in a bit and still make it on time with some added daylight") is a *promise* — if it shows when daylight wouldn't actually improve, the app is lying. The fix is structural: make the helper return `Date | null`, gate every related piece of UI on the same `suggestedDeparture` value, and let the layout reflow when there's nothing to suggest. Worth keeping: when an affordance is conditional on data, hide both the affordance and its supporting copy together — partial truth reads worse than absence.
- **The +15min buffer past sunrise is a visual call, not a wildlife-window-clearing call.** Considered scheduling exactly at sunrise — too close to the horizon to feel "in daylight." Considered +31min to clear scoring.ts's dawn ±30-min wildlife window entirely — but that starts feeling like a different trip rather than "leave in a bit." Settled on +15: short enough to feel like a small wait, long enough to clear the visually-dim band, while explicitly accepting that the first ~15 min of the trip is still inside scoring.ts's dawn window (where wildlife caution is amplified ×2). Documented this trade-off in `suggestedDepartureForDaylight`'s docstring so future readers don't think the +15 was meant to clear the wildlife window — it wasn't. Worth keeping: when two pure-function modules touch related thresholds (here: "is it daylight" vs "is it dawn for wildlife"), let each own its own constant — but document where they overlap so a later reader doesn't assume one was sized for the other.
- **`Date#toLocaleTimeString('en-US', { hour: 'numeric', minute: '2-digit' })` returns "7:38 AM" with no zero-padding on the hour.** That's exactly Figma's intended copy. Hand-rolling `${h}:${m.toString().padStart(2, '0')} ${h < 12 ? 'AM' : 'PM'}` would have shipped — but Intl gives correct AM/PM ordering for any locale (some put it before the hour) and edge-case-handles midnight/noon ambiguity. Worth keeping: trust Intl for human-readable times; only hand-format when you genuinely need a non-locale-standard shape.

## feat/trauma-informed-pulled-over (2026-05-09)

Two trauma-informed UX additions to /pulled-over: tap-to-skip on the transition phase, and review's "Close" now returns to the contact phase instead of dismissing the whole modal. Both are user-pace-control moves backed by Stanford Trauma & Resilience Lab research and ACLU's app-design patterns — the safety flow now bends to the user's processing speed instead of forcing them along its own.

- **Pace control during stress is the strongest predictor of self-regulation** per Stanford's Trauma & Resilience Lab work on stress UX. The previous transition phase had a hardcoded 3-second auto-advance — designed as a calming pause, but for a user actually mid-stop, 3 seconds of forced wait can feel longer than helpful. Now the entire transition card is a Pressable: auto-advance still fires for users who don't tap (default calming pace preserved), tapping accelerates for users who're ready to move. Worth keeping: when the design's intent is "give the user a moment," tap-to-skip is non-destructive — it preserves the moment for users who use it and removes the floor for users who don't.
- **"Close" on the review phase now means "back to contact," not "exit modal."** Old behavior: a user reading the guidance who realized they need to call their trusted contact had to dismiss the entire safety modal and reopen it — restarting the recording flow, losing state. Now Close returns them to the contact phase where Call/Text live, and the modal-exit gesture is the iOS swipe-down (which the modal presentation supports natively). Renamed the button "Back" with the same semantics. Trauma-informed UX: never make recovery require destruction. ACLU's "Mobile Justice" app design follows the same pattern. Worth keeping: when an app has both modal-exit and within-modal-back as concepts, prefer system gestures for exit and explicit buttons for back — gives the user the right tool for each intent.
- **Tappable surfaces during a calming moment need a discoverable affordance, not just an accessible one.** Considered making the transition card silently tappable (no visible hint), since adding a "Tap to continue" line dilutes the calming intent. But discoverability research (NN Group on hidden interactions) shows users who don't know an affordance exists can't benefit from it — and the calming message stays calming with a small footnoteRegular hint sitting 24pt below the subtitle at 0.7 opacity. The hint is half-visible enough not to compete; visible enough to teach. Worth keeping: in stress-state UI, opting users into faster paths beats forcing them — but only if they know the option exists.
- **Trauma-informed design is the most defensible thesis-distinctive accessibility move.** Most "accessibility" work follows WCAG (testable, codified). Trauma-informed UX comes from psychology and social-work research (Stanford TRL, the Trauma-Informed Care field, Just-Action) — it doesn't have a numeric guideline, but it has clinical literature behind it. For a thesis specifically about a Black drivers' safety app, citing trauma-informed design choices alongside WCAG compliance signals that the project read its actual user research, not just the technical accessibility specs.

## feat/typography-accessibility (2026-05-09)

Continuation of the accessibility work — type, spacing, and sizing as accessibility (per WCAG 1.4.4 Resize Text and 1.4.12 Text Spacing). Dynamic Type opt-in for long-read screens, plus relaxed line-height for stress-state copy on /pulled-over. Scoped intentionally to where the research backs the cost: long paragraphs in stress contexts.

- **`allowFontScaling=true` is not enough when you spread `lineHeight` into your styles.** RN's Text component scales fontSize when Dynamic Type is bumped (`allowFontScaling` defaults true), but it does NOT scale an explicit `lineHeight` you pass in style. The project's typography tokens spread `lineHeight: 22` (etc.) into every Text via `...typography.bodyRegular` — so at 1.5× Dynamic Type, fontSize becomes 25.5pt while lineHeight stays 22pt and lines overlap. New `dynamicType(token)` helper in `theme/dynamic-type.ts` reads `PixelRatio.getFontScale()` at render time and scales both fields proportionally. Worth keeping: any RN project that spreads typography tokens with explicit lineHeight needs a scaling helper to be Dynamic-Type-correct, not just `allowFontScaling`.
- **`relaxedLineHeight` (1.6×) for stress-state long reads, backed by Carter et al. 1998.** Default iOS body type ratio is ~1.29× (17pt fontSize / 22pt lineHeight) — visually tight, matches Apple Maps' nav-instruction register. WCAG 1.4.12 Text Spacing wants content usable at 1.5× line-height. Carter et al.'s reading-under-load research and NN Group's elder-user studies both find wider line-height (~1.6×) reduces line-tracking errors during cognitive stress. Applied this only to `/pulled-over`'s `GuidanceBullet` and the review sub-views' `Bullet` — the longest reads, the most stressed reads. Headers + short labels stay on the iOS-native ratio. Lesson worth keeping: WCAG line-spacing rules don't have to be applied uniformly — apply where the research-backed benefit > the layout cost.
- **Compose order matters: `dynamicType(relaxedLineHeight(token))` not the reverse.** `relaxedLineHeight` sets the *ratio* (lineHeight = fontSize × 1.6), then `dynamicType` scales both proportionally. If you flip the order — scale first, then relax — the relax step overwrites the scaled lineHeight using the scaled fontSize, but you'd lose the proportional scaling. Either way works at scale=1, but at scale=1.5 only the right order produces the right visual.
- **Skipped the defensive `maxWidth` cap on long-read containers.** WCAG 1.4.8's 80-char-per-line guidance is real (NN Group says 50–75 ideal), but on an iPhone-only project with 32pt page margins, content width is ~326pt → ~38 chars per line at default body size. Already half the cap. Dynamic Type at max scale only narrows that further. Adding `maxWidth: 600` would have zero current effect and only matter if the project ever lands on iPad — which is out of thesis scope. Worth keeping: defensive caps are valuable when they prevent regression, but adding code that does literally nothing today muddies the diff.
- **Color-contrast pass deferred (intentionally) to thesis paper rather than codebase.** White text on `colors.freshgreen` (#41AD49) contrasts at ~2.95:1 — fails WCAG 1.4.3 AA's 4.5:1 minimum for body text. Apple Maps' system green CTAs (~#34C759) hit ~3.5:1, which is the same trade-off range. Darkening freshgreen to ~#2E8B36 would clear AA but break brand identity. The right move for thesis: name this as a documented limitation in the paper's accessibility section, not a code change. Worth keeping: accessibility compliance and brand integrity sometimes conflict; the resolution lives in documentation, not always in code.

## feat/accessibility-pass (2026-05-09)

Six accessibility improvements grounded in WCAG 2.1 + Apple HIG, bundled on one branch. Each is small individually; the value is in shipping them together so the app crosses from "looks accessible" to "actually accessible" in one merge.

- **#1 Reduce Motion respect.** `usePulseOpacity` (recording dot, contact ring) and Welcome's `Drift` cloud/wind animations now check `AccessibilityInfo.isReduceMotionEnabled()` on mount and subscribe to `reduceMotionChanged`. When on, the loop short-circuits and pins the value at its visible-but-static state (opacity 1 for pulses, translateX 0 for drift). The decoration stays — just no oscillation. Apple HIG's `UIAccessibilityIsReduceMotionEnabled` pattern; WCAG 2.1 SC 2.3.3. Worth keeping: the listener pattern (read on mount + subscribe to changes) is the right shape for any iOS accessibility setting because users can toggle from Control Center mid-session.
- **#2 Differentiate Without Color via `lineDashPattern`.** Zone overlays were color-only (red/yellow/green polygons + polylines). Added `zoneDashPattern` alongside `zoneColors` in `lib/api/zones.ts` — safe is solid, caution is long-dash, avoid is short-dash. Applied via `lineDashPattern` on Polygon + Polyline. iOS-only (the prop silently no-ops on Android), but iPhone-first project. ~5% of men have red-green colorblindness (NIH/NEI); this is the cheapest non-color cue that doesn't require centroid calculations or marker layering. Worth keeping: when "differentiate without color" is the goal, stroke pattern is usually cheaper than icon overlays — and reads at-a-glance from further away than a tiny icon.
- **#4 VoiceOver reading order via `accessibilityElementsHidden`.** Decorative layers were getting announced before content on layered/absolute screens. Hidden Welcome's full backdrop (clouds, wind, hill, sun, Vic) and /home's daylight strip from VO. Both use `accessibilityElementsHidden` + `importantForAccessibility="no-hide-descendants"` (the second is the Android-equivalent prop name; setting both makes the element reliably invisible to screen readers on either platform). Worth keeping: when an element is purely visual atmosphere with no semantic value, the right pattern is to hide it AND its descendants — not to add a generic accessibilityLabel that announces "decorative image" (which is noise).
- **A. `accessibilityIgnoresInvertColors` on illustrations.** iOS Smart Invert tries to skip images but mishandles SVGs rendered via `react-native-svg` and bitmap Image components inside View wrappers. Pinned the prop on Welcome's backdrop, onboarding panels, /permissions visual block, /pulled-over Officer/Trooper images, and `LandmarkMarker`'s frame. Without this, Smart Invert flips the carefully-tuned palette (orange sky → teal, marker pin colors swap, illustrated skin tones invert). One-line addition per element. Worth knowing: any Image/SVG that has a designed color palette — illustrations, branded markers, gradient strips — needs this prop. Functional UI elements (buttons, text) should NOT have it; they're supposed to invert.
- **D. `accessibilityViewIsModal` on /report's transparent modal.** Stack.Screen `presentation: 'modal'` (used by /safety, /pulled-over) handles VoiceOver containment automatically. `presentation: 'transparentModal'` (used by /report's scrim-over-popup) does not — without `accessibilityViewIsModal` on the popup, VoiceOver could navigate to /home or /en-route content under the scrim. Apple HIG modals + WCAG 2.4.3 Focus Order. One prop on the popup root. Worth keeping: the rule is "if your modal isn't a real iOS modal, you have to set the modal flag yourself."
- **E. `announceForAccessibility` on /pulled-over phase transitions.** State changes (armed → transition → guidance → contact → review) now emit a phase-specific announcement ("Are you armed?", "Trusted contact", etc.) so VoiceOver users get verbal confirmation the flow advanced even if their cursor stayed on a now-stale element. Considered `setAccessibilityFocus` instead, but that requires marking the phaseContainer wrapper as `accessible` which would merge all child Pressables into one announce-blob. `announceForAccessibility` speaks the phase identity without disrupting the user's navigation. WCAG 2.4.3 + Apple HIG "Move VoiceOver focus when content changes meaningfully" — the announcement is the lighter-weight equivalent that doesn't fight the existing semantic tree.

Items deferred (named for the next a11y pass, with reasoning):
- **Dynamic Type** support (typography uses hardcoded fontSize) — real refactor, not a tweak. Flag in thesis paper as a known scope limitation.
- **Driving-specific glanceability** (turn-instruction text scaling at speed) — interesting research angle (NHTSA + Apple Maps precedent) but conflicts with Figma fidelity. Discuss in paper, don't ship.
- **Color contrast audit** on freshgreen buttons (white-on-#41AD49 borderline WCAG AA) — needs a real Stark/Contrast pass.

## feat/en-route-fidelity-and-zones (2026-05-09)

Targeted fidelity pass on /en-route — turn card positioning, ETA cluster alignment, side-button glyph unification — plus zone overlay rendering parity with /home (driven by the same `usePreferences().showZones` toggle). The icon swaps and the layout fixes were small individually but compound: the screen now reads like one design language instead of "Phosphor Shield in a sea of Ionicons."

- **The "extra 16pt of paddingTop" trap with SafeAreaView.** `<SafeAreaView edges={['top']}>` already adds the status-bar inset (~47pt on iPhone Pro). Adding `paddingTop: 16` on the child stacked another 16 on top, pushing the turn instruction 16pt too far down vs. Figma's `pt-[47px]`. Removing the explicit padding lets SafeAreaView's inset be the only source of top spacing. Worth keeping: when laying out under SafeAreaView, treat its inset as the design's top-edge padding. Adding more is almost always wrong.
- **`alignItems: 'flex-start'` is the right answer for asymmetric-size siblings in a row.** The ETA cluster has a 41pt-line-height time text next to a 16pt glyph. With `alignItems: 'center'` (the previous code), the glyph centered to the text's mid-line — visually floating mid-air. Figma uses `items-start`, which top-aligns the glyph to the top of the line box. Reads as "subtitle/category indicator" sitting alongside the time, not a satellite. The `gap: 6` was also wrong — Figma has no gap between the spacer/text/glyph. Lesson: when small-with-large vertical sibling positioning feels off, the issue is almost always the alignment axis, not the spacing.
- **One icon family beats the right icon.** Was tempted to track down each Figma raster glyph and pick a perfect match per button. Better: pick the family the project already uses for nav (Phosphor duotone — same as /menu's rows, /en-route's Shield) and switch all the side-buttons to it. ArrowBendUpLeft (turn), Lifebuoy (help), Shield (safety, unchanged), alert-circle Ionicon (Report — the documented orange exception), NavigationArrow (recenter), SpeakerHigh (volume, both turn-card and side-button). The turn-card mic glyph was a bonus catch — it implied "voice control" but the button is actually a volume-mute toggle per Figma; SpeakerHigh tells the right story.
- **Zone overlay is a one-import, two-block change once /home set the pattern.** Added `usePreferences` hook + `Polygon` import + `zoneColors` named export. The render block (`{showZones && allZones.map(...)}`) is a copy from /home with the same dispatch on `geometry`. No new state, no new logic, no new component. The architecture's payoff: a feature that ships on /home ships on /en-route by reading the same preference and dispatching the same render. If we'd built /home with hardcoded zone state instead of `usePreferences`, this would have been a refactor — instead it was a 30-line addition.
- **Hazard glyph in the turn card stayed deferred.** Figma includes a hazard symbol below the turn instruction (matching the "primary turn card hazard notice" feature documented in CLAUDE.md). Implementing it requires the `hazardsNearTurn(turn, zones)` scoring helper that doesn't exist yet, plus the conditional-render logic for when ≤2 categories are crossing threshold. Visual fidelity of the rest of the card landed; the hazard glyph waits for the scoring helper. Worth keeping: when a Figma element's behavior depends on logic that isn't shipped, ship the layout pass without it rather than ship a static-prop version that lies about app state.

## feat/interaction-polish (2026-05-09)

Three small visual-fidelity wins on one branch — press-state feedback on Pressables app-wide, haptic feedback on key actions, and a status-bar style audit. Each is mechanically simple; the impact is in the texture of the app feeling like an iOS-native build instead of a stylized React Native demo.

- **Press-state via a single `pressedDim` constant + inline functional-style.** Tried three patterns before settling on this one: (a) a `<PressableDimmed>` HOC re-export — reduced edits but obscured the convention; (b) a `pressDim(style)` helper function — cleaner per call site but adds an indirection layer; (c) **`{ pressed } => [styles.x, pressed && pressedDim]` with a single shared constant** — verbose at the call site but explicit, copy-pasteable, and keeps the pattern visible to future readers. Picked (c) because the project's style is to favor explicit RN idioms over HOCs/helpers when the cost of inline is just ~50 chars. The constant lives in `theme/interaction.ts` so a future change (different opacity, scale, or color shift) lands in one place.
- **Haptics map to *moments*, not buttons.** First instinct was to fire haptics on every Pressable. Wrong instinct — that's just buzzing noise. The right model: map haptics to **discrete moments of consequence**. Five chosen:
  - **Apple Sign In success** → `notificationAsync(Success)`. The Apple sheet is a black-box modal; the success haptic confirms completion before /home or /onboarding paints.
  - **Continue chain advances** (onboarding → permissions → trusted-contact) → `selectionAsync()`. Subtle iOS picker-wheel "click" — present but not loud.
  - **Submit Report success** → `notificationAsync(Success)`. The contribution moment lands as a tactile confirmation alongside the Thank-You frame.
  - **Long-press save home** → `impactAsync(Light)`. Mirrors iOS Maps' pin-drop thump — without it, the long-press gesture feels uncertain.
  - **Pulled-over armed answer** → `impactAsync(Heavy)`. The most consequential haptic in the app: the moment the safety flow turns from "what's happening" into "what to do." Heavy weight cues "your answer landed and we're actively helping now."
  - **Call/Text trusted contact** → `impactAsync(Medium)`. The last sensory cue from Fresh Greens before the dialer/Messages takes focus.
- **`.catch(() => {})` after every `Haptics.*` call.** All Haptics methods return promises that can reject if the device doesn't support haptics (e.g., older iPad models, simulator). A rejected promise without a catch is an unhandled rejection in dev. The empty `.catch()` makes haptics fire-and-forget — they enhance the experience when present, do nothing when absent, and never crash. Worth keeping: any non-critical platform API call should swallow its rejection silently.
- **Status-bar audit was a 5-minute pass with zero fixes.** All 15 routes already had appropriate `style="light"` or `"dark"` based on their primary background (light on wiltedgreen/orange/burntgreen, dark on white/map). The pattern was set early and has held through every subsequent screen. Worth recording as a reminder: when a convention is right at the start, audits later are confirmation passes, not fix-up passes. Ranking it highly in "low-effort visual wins" turned out to be wrong — the win was already banked.

## feat/permissions-settings-recovery (2026-05-08)

Closes the "previously declined" silent-advance gap on /permissions. iOS only shows a permission prompt once — after the first "Don't Allow," `requestForegroundPermissionsAsync()` and `requestRecordingPermissionsAsync()` return the cached deny state immediately, no system dialog. Without a visible escape hatch, the user tapped Continue and advanced to /trusted-contact-setup with no permissions granted and no UI feedback. Now an inline footnote-link recovery affordance ("Previously declined? Open iOS Settings") appears below Continue when `canAskAgain === false` for either permission.

- **`canAskAgain` is the right signal, not `status === 'denied'`.** Both `expo-location` and `expo-audio` return a `{ status, canAskAgain }` shape. The deny-vs-permanent-deny distinction matters: `denied` could be a fresh denial that the OS will still re-prompt for under some flows, while `canAskAgain === false` is the precise "OS won't prompt again, period" signal — that's what controls whether the recovery affordance is needed.
- **`useFocusEffect` not `useEffect` for re-checking on return.** The recovery flow goes app → iOS Settings → user toggles → app. When they come back, the screen is already mounted (no re-mount), so a `useEffect([])` would never re-fire. `useFocusEffect` from expo-router fires on every focus, including return-from-Settings, so the affordance disappears once they grant permission. Subtle but important — without it, the link would persist incorrectly until navigation.
- **Reused the inline-link register from Get Started, didn't invent a new one.** "Previously declined? Open iOS Settings" mirrors Get Started's "Already have an account? Log in" — footnoteRegular white prompt with a freshgreen underlined action span. No new design tokens, no new component, no new color. When the design system already has a pattern for "secondary action below the primary CTA," the right move is to reuse it — exactly the conversation that came out of audit 7's cursorrules-exception cleanup.
- **`Linking.openSettings()` opens the app's page, not the root.** Tapping the recovery link drops the user directly into Fresh Greens' iOS Settings page where Location and Microphone toggles are visible. No "navigate to Privacy → Location → find Fresh Greens." This is RN built-in, no dependency added — the iOS-specific `app-settings:` URL scheme wrapped behind a cross-platform API.

## fix/onboarding-illustrations-svg — full-bleed + Vic + SVG-default rule (2026-05-08)

Second pass on the same branch. After the first round on phone, two things were off: the onboarding illustrations stopped just above the Continue button instead of bleeding to the screen edge (Figma puts Continue *on top* of the illustration, not above it), and Vic on the Welcome screen was the last 1x PNG holdout — went visibly blurry at the same densities the onboarding panels had. Same branch now bleeds illustrations to the bottom edge with Continue/Skip overlaying, Vic is SVG, and CLAUDE.md gained an "Asset format default: SVG" rule so this pattern doesn't repeat.

- **Layout root cause: the SafeAreaView was the constraint.** Original tree was `<SafeAreaView><PageControl/><FlatList/><Actions/></SafeAreaView>`. The FlatList was bounded by Actions on the bottom — so `bottom: 0` on the illustration anchored to the *top of Actions*, not to the screen edge. Fix: take the FlatList out of SafeAreaView, give it `StyleSheet.absoluteFillObject`, and use `useSafeAreaInsets()` to manually pad the foreground UI. The foreground sits in its own absolute-fill container with `pointerEvents="box-none"` so swipes pass through to the FlatList everywhere except where the buttons want them. Worth keeping: when "the illustration won't go all the way to the bottom" is the symptom, the parent's bottom edge is doing the bounding — not the illustration's `bottom: 0`.
- **`pointerEvents` is the answer to "two stacked layers, both want input."** PageControl + Continue need taps; the FlatList behind needs swipes to get through everywhere else. `box-none` on the foreground container says "I don't catch touches, my children might"; nested `pointerEvents="auto"` on the action wrapper opts back in for the buttons. Without this, either swipes wouldn't register over the bottom area or button taps wouldn't fire.
- **PNG-to-SVG audit: the threshold is dimension, not category.** Onboarding panels were 1x PNGs and looked fine in development for weeks because simulator @1x displays match the source bitmap. Real iPhone hardware is 2x or 3x; that's where the blur showed up. Working rule now in CLAUDE.md: **if it's vector in Figma and over ~48pt in either dimension, default to SVG.** Below that threshold, bitmap blur is below perception. Above it, you'll catch it eventually — and the cost of fixing late is rebranching, re-exporting, retesting, repushing. The cost of doing it right at upload time is zero.
- **Vic is the exception that proves the SVG rule. Image fills don't survive the SVG export.** Tried to swap Vic from PNG to SVG, expected the same crispness win the onboarding panels got. Got a broken render: Vic scaled up wrong, the location-pin shape clipped at the SVG's bounds and reappeared on the opposite edge. Root cause: Vic's Figma source uses **image fills** (raster textures inside vector shape masks — that's how the hand-painted skin/clothing texture is achieved). Figma exports image fills as `<pattern patternContentUnits="objectBoundingBox" width="1" height="1">` wrapping a base64 PNG. `react-native-svg` doesn't render those reliably — the pattern's intrinsic raster size doesn't map to the fill rect, so it tiles, scales wrong, or wraps. Critically, **Figma's "Flatten" command does NOT fix this** — it merges paths but keeps the image fills intact. Confirmed by re-exporting after Flatten and grepping for `<pattern` in the SVG: same patterns, same problem. The only paths to a pure-vector Vic would compromise the illustration itself (replacing image fills with solid colors loses the texture). So Vic ships as `welcome-vic.png` (a 498×677 source displayed at 166×226 — Metro downsamples on render). Filename has no `@3x` suffix: Metro reads `@Nx` as a density tag and expects a 1x base alongside, so the import fails on a bare `@3x` filename. Single high-density bitmap referenced as a plain filename is simpler and resolves cleanly. CLAUDE.md's asset rule was tightened with this exception clause: image-fill layers → @3x PNG, not SVG. Worth keeping: when an SVG renders unexpectedly in react-native-svg, `grep -c "<pattern"` is the fast diagnostic — patterns are the most common rendering gap between RN and browser SVG.
- **CLAUDE.md gained two unrelated additions in the same pass.** "Why zones exist" (Architecture section) and "Hazard notice on the primary turn card" (En-route follow-ups) landed alongside the asset fixes. Bundling docs with code is fine when the docs are about the same conceptual area as the change ("how zones surface in the UI" pairs with "how illustrations surface in the UI" — both are visual-fidelity concerns). Worth being honest that this widens the PR's review surface; if the docs raise questions, easy to split into its own PR.

## fix/onboarding-illustrations-svg (2026-05-08)

- **`isPointInRegion` is a literal lat/lng box check, not a haversine distance.** Tempted to use the distance-from-center formula, but the visible region is a rectangle in lat/lng space (not a circle), so a box check is both faster and correct. The math: `lat ∈ [center.lat - delta/2, center.lat + delta/2]`, same for lng. Worth knowing for anything that asks "is this point in the visible map" — RN-maps' `Region` already gives you the deltas, no haversine needed.
- **Sign-out cleanup needs to grow with new identity-attached state.** Adding `useSavedPlaces` introduced a new AsyncStorage key tied to the user. Without updating `/menu`'s `handleSignOut`, the next sign-in (potentially a different Apple ID) would inherit the previous user's saved home. Easy to forget — the sign-out function lives in a different file from where the new state was added. Worth noting as a project convention: every new "user-scoped" adapter must be added to `handleSignOut`'s `Promise.all` cleanup.

## feat/welcome-cloud-animation (2026-05-06)

Splits the Welcome backdrop composite into individual layers so the clouds + wind elements can drift independently. Each animated element is wrapped in a `Drift` helper that runs an `Animated.loop(Animated.sequence([...]))` translateX oscillation with `Easing.inOut(Easing.sin)` and `useNativeDriver: true`.

- **Composite-vs-individual is a one-way door for animation.** The previous PR's single `welcome-backdrop.png` was the right call for v1 — exact Figma fidelity, one asset, simple layout. But you can't animate a sub-region of a baked PNG. The moment "make the clouds move" became a goal, the composite had to be torn apart into 14 individual layers (Vic PNG + 13 SVGs) all absolutely positioned per the Figma authored coords. Worth knowing for future "static composite OR animated layers" decisions: pick based on whether motion is in scope. If motion is plausible later, lean toward individual layers from the start to avoid the rework.
- **`useNativeDriver: true` on translateX is essentially free.** The 10 simultaneous looping animations (7 clouds + 3 winds) run on the UI thread without touching the JS bundle. No frame drops on the splash screen, no contention with `useUser`'s AsyncStorage read or the `router.replace('/home')` redirect during the cold-start path. Lesson: any time the only animated property is transform/opacity, set `useNativeDriver: true` — it's a strict perf upgrade with no downside.
- **Per-element duration variance > random phase offset for desync.** First instinct was to randomize each cloud's starting phase (`Animated.Value(Math.random() * amplitude)`) so they wouldn't move in lockstep at t=0. Settled instead on giving each cloud a different `duration` (2.8s–5.8s spread across the 10 elements) — the desync emerges naturally after the first cycle, and starting them all at offset 0 keeps the initial frame faithful to Figma's authored composition. Random phase would also break determinism (snapshot tests would flake). Worth knowing: when orchestrating multiple looping animations, varying their periods is enough to prevent visible synchronization, no random offset needed.
- **`Easing.inOut(Easing.sin)` reads as "ambient drift" specifically.** Linear easing makes clouds look like they're on rails. `Easing.inOut(Easing.cubic)` is too aggressive (clouds visibly slow at the edges). `Easing.inOut(Easing.sin)` is the closest analog to natural air drift — slows almost imperceptibly at the extrema, accelerates smoothly through the middle. Worth saving for any "subtle motion" use case where the goal is to make motion feel organic rather than digital.
- **390×846 reference frame, bottom-centered, on a wider device.** The backdrop scene is a fixed 390×846 container wrapped in `alignItems: 'center'` + `justifyContent: 'flex-end'`. On iPhone Pro Max (430-wide), there's ~20pt of empty orange on each side at the top corners — invisible because the orange backgrounds match the root color. On iPhone SE (smaller height), the scene gets clipped at the top (border cloud peeks off-screen) but the hill stays anchored at the bottom. Worth knowing: when you have a fixed-aspect illustrated scene that needs to pin to one edge across device sizes, bottom-aligning the entire scene gives the most predictable hill/horizon behavior.

## feat/recordings-list (2026-05-06)

Builds the audio library for /pulled-over's safety captures: `lib/api/recordings.ts` adapter, `useRecordings` hook, `/recordings` screen with inline playback + delete, /pulled-over auto-saving on dismiss. Compromise: yes, opening an iOS contact picker during a stop is suboptimal. But "out of luck" is a much worse failure mode than "extra friction." Lesson: when shipping a flow that depends on prior setup, audit every "user skipped that setup" path and at minimum offer a recovery affordance. Hiding the feature behind onboarding alone is a bug magnet.
- **Defensive UI fallbacks pay off when data shape changes mid-development.** Stored contacts saved with `name: undefined` don't disappear when the adapter learns to derive names — they sit in AsyncStorage until cleared. ContactView's `contact?.name?.trim() || contact?.phoneNumber || NO_CONTACT_NAME` chain handles all three cases (real name, broken stored contact, no contact) without stranding the user on a contact they can't re-pick. ## feat/trusted-contact-end-to-end (2026-05-06)

Second "make it real" PR after Apple Sign In. Adds the trusted-contact picker (iOS-native via `expo-contacts`), wires the pulled-over contact phase to read it, and turns Call/Text into real `Linking.openURL('tel:…')` / `sms:…` actions. Also moves mic permission from mid-stress (during /pulled-over) to calm onboarding.

We get a real native UX (familiar iOS picker, same as iMessage/Phone use), no permission dialog, no "show all contacts in our own UI" rabbit hole. Picker-style flows beat permission-then-list flows when the data scope is "one item I'm choosing right now."
- **Adapter shape stayed identical to user.ts.** Same `getX / setX / clearX` async surface, same AsyncStorage backing, same backend-swap-point comment. The third adapter using this pattern (zones / community-reports / user / trusted-contact = four now) means it's a real codebase convention, not a one-off. Future identity-style adapters (recordings, recent trips) should slot into the same shape.
- **Store only what the safety flow needs.** Contacts on iOS can be huge — addresses, social profiles, photos, all the postal labels. Caching the full Contact would be both privacy-sloppy and storage-wasteful. We extract `id`, `name`, `initials` (derived at save), `phoneNumber` (primary or first), `setAt` and persist that. - **`tel:` / `sms:` URI schemes are platform-agnostic and reliable.** No platform-specific code needed; `Linking.openURL('tel:+1...')` works on iOS and Android. The number's format barely matters — both accept formatted (`(212) 555-0123`) and unformatted (`2125550123`). Worth knowing this isn't a fragile area; the brittle thing in real-call wiring is *getting* the number, not *using* it.

That's a deliberate Plan A scope decision (Settings is its own next PR). It works because thesis-demo users go through onboarding once. The lesson is granular: when a feature has a setup phase and a use phase, you can ship just the setup phase + use phase first, and defer the *edit* phase until you have user feedback on what edit affordances actually need to exist.
- **Permission asks back-to-back are OK on iOS.** Originally I worried about "two dialogs in a row" feeling intrusive at /permissions (location then mic). It actually reads fine — iOS treats them as separate, sequential prompts; the user understands each one. The key is they're both contextually justified by the same screen ("we need these for routing + safety recording"). Not lumping them into a single "grant everything" prompt.
- **Onboarding momentum > permission gating.** /permissions originally dead-ended at iOS Settings on denial — the user had to leave the app, toggle the permission, swipe back, and tap again. That's a stall in the middle of a one-time flow. Better: always advance after the prompts fire, regardless of grant/deny. The app degrades gracefully without either permission. Users who denied can grant later via system Settings; they don't need to grant *right now* to keep moving. Lesson: onboarding should never have a "you can't continue without this" wall unless the feature is genuinely useless without it.
- **Phosphor's barrel index breaks Metro at scale.** `import { UserPlus } from 'phosphor-react-native'` triggers Metro to bundle the barrel — which re-exports ~9000 icons. Any single icon's resolution failure (we hit `./icons/Bank` for unclear reasons) crashes the entire bundle. Fix: deep-import via `phosphor-react-native/src/icons/UserPlus`. Metro now bundles only the one icon. Side-effect: TypeScript follows the deep `.tsx` source instead of the barrel's `.d.ts` and starts type-checking phosphor's strict-incompatible internals (`className` on Svg). `skipLibCheck` doesn't help because it skips `.d.ts`, not `.tsx` from `node_modules`. Two-tool, two-paths solution: TS uses `lib/typescript/icons/*`, Metro uses `src/icons/*`. Worth knowing this gotcha before reaching for any icon library that ships a giant barrel.

## feat/auth-apple-signin (2026-05-06)

First "make it real" PR after the audit. Wires Apple Sign In via `expo-apple-authentication`, adds the missing `/login` screen, and introduces the user-identity adapter (`lib/api/user.ts`) + reactive hook (`hooks/useUser.ts`).

- **Adapter pattern carries to identity.** `lib/api/user.ts` follows the same shape the zones / community-reports / routes adapters use — typed `User`, async public surface (`getStoredUser`, `setStoredUser`, `clearStoredUser`, `upsertUser`), AsyncStorage internals as the v1 backing store, with the backend-swap point clearly marked. Identity now flows through the same architectural register as everything else, which is the win: a future Supabase swap is a single-file change, not a cross-screen refactor. The thesis claim of a typed-adapter pipeline now holds for auth too, not just data.
- **Apple's first-sign-in-only behavior is a real architectural concern.** Apple returns `fullName` and `email` only on the user's *first* sign-in to an app. Returning sign-ins return only the stable `user` ID. If you naively persist what Apple gives you each time, returning users overwrite their cached display name with nulls. `upsertUser` solves this by merging — newest-wins, but `null` doesn't overwrite a real value. This is the kind of provider quirk that's easy to miss until a returning user shows up with their initials reading "?".
- **Routing decisions belong at the call site, not in the auth hook.** `useUser`'s `signInWithApple` returns the freshly-stored User and stops. The caller (`/get-started` vs `/login`) decides where to navigate post-sign-in — first-time → `/onboarding`, returning → `/home`, login screen always → `/home`. Hooks shouldn't have opinions about flow; they should have opinions about state. Keeping the hook flow-agnostic means it slots into Settings sign-out / re-auth later without rewiring.
- **First-time vs returning is checked from storage, not from Apple's response.** Apple's `signInAsync` doesn't tell you whether this is the user's first time on this app. `getStoredUser()` *before* the sign-in does — if there's already a user record, this is a returning sign-in. Simple, source-of-truth-y, doesn't depend on provider quirks.
- **Auto-redirect needs a `loading` guard.** Welcome's auto-redirect for signed-in users (`if (!loading && user) router.replace('/home')`) requires waiting on the AsyncStorage read. Without the guard, `user` is briefly `null` on cold start even when a user IS stored, and Welcome would either flash and bounce, or worse, leave a signed-in user staring at the splash. The pattern is: don't navigate on absence-of-information, only on confirmed-information.
- **Auth + login as one PR is the right granularity.** Splitting them would have meant Welcome → /login routing nowhere meaningful for a stretch, OR a half-built login screen sitting in code without a destination. Bundling the two means main always has a working flow — the user can sign up, sign in, return, and re-enter the app coherently from the moment this lands. The "next PR" pattern (this one's a foundation; trusted-contact picker + recordings list build on top) keeps each branch small and testable while never landing a half-feature.
- **Visual reuse held off on extraction.** /login is a near-clone of /get-started's layout but routes differently and has different copy. Resisting the urge to extract a shared `<AuthScreen />` component before there's a third use — applying the rule of three. When Settings ships with a sign-in surface, that'll be the third use, and *then* the shared component will know what its real shape needs to be.
- **`usesAppleSignIn: true` in app.json + the plugin install + the entitlement = three things that all have to land together.** Forgetting any one breaks the sign-in sheet at runtime in ways the dev hasn't seen since the previous Expo SDK migration. Worth a one-time mental note: every iOS-entitlement feature has this three-part dance.

## feat/routing-formula-zones (2026-05-06)

The remaining three thesis factors — police, wildlife, road conditions — land as OSM-fed zones through the existing pipeline. What we did, in plain terms:

- **The discriminated union earned its keep again.** Adding three new categories to the routing formula meant: extend the Overpass query union, add new tag dispatchers in the parser, add new entries in mock fallback. **No change** required to `pickWinner`'s public signature, no consumer changes in /home or /en-route, no scoring inner-loop rewrite. Discriminated `geometry: 'polygon' | 'polyline' | 'point'` made the geometry side trivial; adding optional `category: ZoneCategory` made per-source modulation possible without touching the type system everywhere else. Three new data sources, ~200 lines of net adapter additions, zero ripples.
- **Time modulation belongs in scoring, not in the zones adapter.** The dawn/dusk wildlife multiplier could've been baked into the zone (compute "is it dusk" at fetch time, return type='avoid' instead of 'caution'). Doing it in scoring is cleaner: zones describe *what's there*; scoring decides *what to do about it given the trip context*. Trip context (departureTime) lives at the call site of `pickWinner`, not at the time of fetching zones — and a route may be re-scored against the same zones for different scheduled departures (the future "Schedule for 7:38 AM" feature). Single source of zone truth, multiple scorings as needed.

Lesson: when extending an Overpass query, check whether the new tag families use way/node/both before assuming the existing parser shape covers them.
- **`departureTime` defaults to `new Date()` so adding the param wasn't a breaking change.** Existing call sites in /home and /en-route still call `pickWinner(rawRoutes, allZones)` with no third argument — they implicitly mean "leave now," which is what most trips are. - **Mock fallback grew with the categories.** Original mock was 3 polygons covering safe/caution/avoid. With the new categories shipping behind the same `SHOW_ZONES` debug toggle, the mock needed to demonstrate police/wildlife/road-condition zones too — otherwise the demo screenshot would be misleading when Overpass is unreachable. Six mock zones now, one per category. Mock fidelity is part of the demo experience, not a fallback afterthought.

Master = single source of truth (the extracted function/component); instances = each use site (each call). Props = instance overrides. Detaching = inlining. - **Expo + npm 7+ peer-dep conflicts are routine.** `--legacy-peer-deps` is the official Expo workaround. Adding `.npmrc` with `legacy-peer-deps=true` makes it permanent, sticky across collaborators and CI. Industry-standard for Expo SDK 50+.
- **`<MapView>` is a native bridge component**, not a JS-only React component. It wraps Apple MapKit on iOS and Google Maps on Android. Map tiles, gestures, animations all happen at the native layer — JS just hands props.
- **`initialRegion` vs `region`.** `initialRegion` (uncontrolled) sets the starting viewport; user pan/zoom is preserved. `region` (controlled) forces the map back on every render. Use the former for normal navigation, latter for "snap to a specific location" features.
- **Apple MapKit allows overlays but not basemap restyling.** Custom routes, markers, zones all draw on top of the map ✓. Restyling streets/labels themselves ✗. Fresh Greens' route customization lives in the data + overlay layer, not basemap geometry — so MapKit is sufficient. Switch to MapLibre/Mapbox only if dark-mode or fully custom basemap aesthetics become essential.

## feat/onboarding-2 (2026-05-03)

- **Extract on the third use, not before.** Two inline copies of the page-control pattern stayed inline. The third occasion is when you write `<PageControl />` for the first time — and at the same time, retrofit the two prior consumers to use it. Earlier extraction over-fits to the first variant; later extraction accumulates drift between copies.
- **Replicate Figma's structure 1:1 when reasonable.** Figma's "Page Control" is an h-44 wrapper with the dots vertically centered. Translating that as `height: 44` + `alignItems: 'center'` (instead of guessing at paddingVertical math) keeps the design-to-code mapping legible. Whoever opens Figma and the file should see the same shape on both sides.
- **`false` in a style array is a no-op.** `style={[styles.dot, isInactive && styles.dotInactive]}` evaluates to either `[styles.dot, styles.dotInactive]` or `[styles.dot, false]`. RN's array merger silently ignores the `false`. Cleanest conditional-style pattern.
- **`Array.from({ length: n }).map((_, i) => ...)`** is the canonical "render n elements" pattern when you don't have a real array of data. The underscore signals "we don't care about the value, only the index."
- **`justifyContent: 'space-between'` doesn't mean buttons are pinned independently.** When the top child grows, the distributed gap shrinks; the bottom child stays at the bottom but appears closer to the body. Not a bug — feature of how the flex distribution works. The fix when this matters is usually a missing illustration filling the middle, not a layout change.

## chore/typography-tokens (2026-05-03)

- **Spread + override is the canonical token consumption pattern.** Spread the token to inherit the contract (size, weight, letter spacing), then add overrides (color, alignment, decorations) below. Reads top-down as "what kind of text + what's special about this instance."
- **Pull a single property when nested Text inherits.** For inner `<Text>` inside an outer `<Text>`, RN inherits size/lineHeight/letterSpacing automatically — only override the property that differs (e.g. `fontWeight: typography.footnoteEmphasized.fontWeight`). Spreading the whole token would re-apply already-inherited values redundantly.
- **A successful refactor has zero visual diff.** "Looks identical" is the success state. If something looks different post-refactor, the token or the consumer is wrong.

## feat/onboarding-1 (2026-05-03)

## feat/permissions (2026-05-03)

- **JSX nesting often needs to mirror Figma's group nesting.** A Figma group with `gap: 32` between visual-block and CTA isn't decorative — it's load-bearing structure. Flattening it into siblings of the SafeAreaView lost the relationship and put the CTA at the bottom instead of 32pt below the sub-instructions.
- **`alignItems: 'flex-start'` cascades through wrapper Views.** Each level inherits "be as small as your kids," which collapses long Text down to its intrinsic line width and visually swallows parent padding. Default `alignItems: 'stretch'` lets wrappers fill the cross-axis so Text wraps within the proper width.
- **The robust pattern: default `stretch` + `alignSelf` overrides on exceptions.** Don't flip the parent's `alignItems` and then compensate everywhere; let stretch be the default and add `alignSelf: 'flex-start'` (or `center`) only on the children that need different behavior.

- **TEMP-wire pattern for testing in-progress routes.** When a screen exists but isn't reachable from the proper flow yet, temporarily wire an existing button to navigate there, with a clear `// TEMP:` comment so it's grep-able and obviously not permanent. Better than building a hidden dev menu just for one route.

## feat/screen-illustrations (2026-05-02)

- **`<Image>` needs explicit width AND height.** The `left: 0, right: 0` shorthand that implicitly widths a `<View>` doesn't reliably work on Image — RN can fall back to the asset's natural pixel size (huge, since 3x exports are 3× the design dimensions). Always set `width` explicitly.
- **`require('../path/to/file.png')` bundles a local asset at build time.** Different from `source={{ uri: 'https://...' }}` which fetches a remote URL at runtime. Metro reads `require()` calls statically and packs the file into the app bundle.
- **`resizeMode="contain"` fits the image inside its bounds preserving aspect ratio.** Other options: `cover` (fills, may crop), `stretch` (fills, may distort), `center` (no scaling). `contain` is almost always right for illustrations.
- **`transform: [{ translateX: N }, { translateY: M }]` shifts an element visually without affecting layout flow.** Negative Y = up (screen coords have y pointing down). Use for fine-tuning position without cascading into siblings.
- **JSX source order = paint order for overlapping absolute siblings.** Earlier in JSX = behind, later = in front. No `z-index` needed for sibling overlaps. Useful for masking via overlap (sun behind hill = clean rising-sun silhouette without a pre-clipped asset).
- **Centering an absolutely-positioned element:** `left: '50%', marginLeft: -<half-width>`. The `left: 50%` puts the *left edge* at center; the negative margin pulls the element back so its *center* sits on center. Same trick vertically with `top` + `marginTop`.
- **`accessible={false}` on decorative images** tells VoiceOver to skip them. Sun, clouds, atmospheric art = decorative; UI icons that convey meaning = `accessible={true}` with a label.
- **New asset directories sometimes need `npx expo start -c`** to be picked up by Metro's file watcher. Hot reload works for code changes but can miss brand-new directories.

## feat/get-started (2026-05-02)

- **`onPress={handler()}` runs at render time and is almost always wrong.** `onPress` wants a function, not the result of calling one. Three forms: `onPress={fn}` if no args, `onPress={() => fn(arg)}` if args, never `onPress={fn()}`.
- **Arrow function `() => expr` is shorthand for `function() { return expr }`.** Defines an anonymous function that runs `expr` when called.
- **`useRouter()` is a hook — call it at the top of the component**, not inside conditionals or loops. Hooks always start with `use`.
- **`router.push('/path')` matches a file at `app/path.tsx`.** That's the file-based routing magic — no manual route registration.
- **Pattern reuse from screen to screen is a trap.** Welcome had a curved hill; I copied the same View+borderRadius onto Get Started without checking the design — but Get Started's divider is *flat*. Look at the design first, name the shape, then decide whether to reuse. Anti-slop rule "match existing patterns" only applies when the new screen actually wants the existing pattern.
- **Name styles by what they are, not where they came from.** `hill` implies a curve; `ground` describes a flat lower section. Future-you reading the file shouldn't have to guess.

## feat/welcome (2026-05-01)

- **Git commits live in `.git/` locally — they're real before you push.** GitHub is just a hosted copy. `git push` is backup + share, not "make the commit count."
- **`git checkout -b` = create a branch *and* switch to it.** `-b` is `--branch`, the create flag.
- **`-u` on `git push` sets upstream tracking.** First push only; later pushes are just `git push`.
- **`as const` on a TS object literal** narrows the inferred types from `string` → exact literals. Combined with `keyof typeof`, that's how you get a union type of valid color names.
- **In RN, `borderRadius` clamps to half the element's width.** A 240 radius on a 390-wide View becomes 195 on each top corner — and two 195-radius quarter-circles meeting at the top-center give a tombstone dome, not a hill. Fix: extend the element past the screen edges + much larger radius. Only the gentle middle of the arc shows.
- **RN layout is bottom-anchored when actions are pinned to the bottom.** To move a sibling *up*, increase the gap *below* it (its `marginBottom`), not the space above it. Backwards from web instinct.
- **`StyleSheet` has no units.** Numbers are density-independent pixels; same physical size on iPhone SE and Pro Max.
- **`fontWeight` in RN is a string, not a number.** `'700'`, not `700`. Trips everyone up once.
- **`Text` can't sit directly inside a `View` as a string.** Always wrap in `<Text>`. Different from HTML.
- **Built-in `SafeAreaView` is the simpler version.** `react-native-safe-area-context` is the more capable replacement we'll swap in when the built-in misbehaves (landscape, side notches, custom inset positioning).
