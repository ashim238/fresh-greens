## chore/figma-fidelity-audit-5 (2026-05-07)

Fifth audit after 6 feature PRs landed since #4 (auth, trusted contact, menu hub, menu rework, recordings, illustrations + cloud animation). Ran a static sweep for the documented drift patterns — hardcoded widths, raw hex colors, fontSize/fontWeight overrides, fix-trace comments, stale TODOs — then fixed the small wins inline. Lighter-touch audit than #4 because most recent PRs included self-review polish passes; the surviving drift was almost entirely **stale comments** rather than design-system violations.

- **Static sweep > screen-by-screen Figma diff for routine audits.** Pulling 12+ Figma frames and visually comparing is expensive (tokens + time) and mostly redundant when no design has changed since the last audit. A grep pass for the documented anti-patterns (`width: 374`, raw `#XXXXXX` outside theme, inline `fontWeight`, `// TODO: install <dep>`) catches 90% of real drift in seconds. Reserve full screen-by-screen Figma diffs for audits *after* a Figma update, not after a code-side feature run.
- **Stale TODOs accumulate even when tasks ship.** Both `home.tsx:404` ("TODO: install expo-linear-gradient") and `home.tsx:462` ("once we install a sun calculator") referenced deps that had been installed *and used* — `LinearGradient` rendering five lines below the first TODO, suncalc threading through `lib/daylight.ts`. The shipping commit didn't update the now-misleading TODO. Lesson: when finishing work that resolves a TODO, search for the exact phrase ("install X", "TODO: X") and either delete the comment or rewrite it to capture what's still genuinely outstanding.
- **Stale dimension comments outlive the code's responsiveness.** `get-started.tsx` had two comments referencing `width: 326` ("Content wrapper: width: 326", "fills contentInner's 326pt") long after the actual implementation was rewritten to `alignSelf: 'stretch'` for Pro Max responsiveness. The 326 was a Figma-baseline number that earned its place in early commits as documentation but became misleading when the implementation surpassed it. Lesson: when you flip a hardcoded value to a responsive pattern, audit the comments naming the old value — they become a trap for the next reader.
- **`.gitignore` for sibling repos in the same checkout.** Cloning the public design-system specimen *inside* the private fresh-greens checkout produced a persistent `fresh-greens-specimen/` untracked entry in `git status`. Added an explicit ignore rule with a comment pointing to the canonical location. Worth knowing: when you have two related repos and one ends up nested locally, the right answer is `.gitignore`, not "remember not to commit it" — `git add -A` would have swept it in eventually.
- **Audits get lighter as self-review-on-PR matures.** #1 and #2 caught major drift (token mismatches, hardcoded widths, ACLU copy errors). #4 was already lighter. #5 was almost entirely comment cleanup because recent PRs (`feat/illustrations`, `feat/welcome-cloud-animation`) shipped explicit `chore:` commits trimming slop *before* merge. The audit cadence stays valuable as a baseline-reset, but the per-audit fix volume has been declining — that's the system working.

## feat/welcome-cloud-animation (2026-05-06)

Splits the Welcome backdrop composite into individual layers so the clouds + wind elements can drift independently. Each animated element is wrapped in a `Drift` helper that runs an `Animated.loop(Animated.sequence([...]))` translateX oscillation with `Easing.inOut(Easing.sin)` and `useNativeDriver: true`.

- **Composite-vs-individual is a one-way door for animation.** The previous PR's single `welcome-backdrop.png` was the right call for v1 — exact Figma fidelity, one asset, simple layout. But you can't animate a sub-region of a baked PNG. The moment "make the clouds move" became a goal, the composite had to be torn apart into 14 individual layers (Vic PNG + 13 SVGs) all absolutely positioned per the Figma authored coords. Worth knowing for future "static composite OR animated layers" decisions: pick based on whether motion is in scope. If motion is plausible later, lean toward individual layers from the start to avoid the rework.
- **`useNativeDriver: true` on translateX is essentially free.** The 10 simultaneous looping animations (7 clouds + 3 winds) run on the UI thread without touching the JS bundle. No frame drops on the splash screen, no contention with `useUser`'s AsyncStorage read or the `router.replace('/home')` redirect during the cold-start path. Lesson: any time the only animated property is transform/opacity, set `useNativeDriver: true` — it's a strict perf upgrade with no downside.
- **Per-element duration variance > random phase offset for desync.** First instinct was to randomize each cloud's starting phase (`Animated.Value(Math.random() * amplitude)`) so they wouldn't move in lockstep at t=0. Settled instead on giving each cloud a different `duration` (2.8s–5.8s spread across the 10 elements) — the desync emerges naturally after the first cycle, and starting them all at offset 0 keeps the initial frame faithful to Figma's authored composition. Random phase would also break determinism (snapshot tests would flake). Worth knowing: when orchestrating multiple looping animations, varying their periods is enough to prevent visible synchronization, no random offset needed.
- **`Easing.inOut(Easing.sin)` reads as "ambient drift" specifically.** Linear easing makes clouds look like they're on rails. `Easing.inOut(Easing.cubic)` is too aggressive (clouds visibly slow at the edges). `Easing.inOut(Easing.sin)` is the closest analog to natural air drift — slows almost imperceptibly at the extrema, accelerates smoothly through the middle. Worth saving for any "subtle motion" use case where the goal is to make motion feel organic rather than digital.
- **390×846 reference frame, bottom-centered, on a wider device.** The backdrop scene is a fixed 390×846 container wrapped in `alignItems: 'center'` + `justifyContent: 'flex-end'`. On iPhone Pro Max (430-wide), there's ~20pt of empty orange on each side at the top corners — invisible because the orange backgrounds match the root color. On iPhone SE (smaller height), the scene gets clipped at the top (border cloud peeks off-screen) but the hill stays anchored at the bottom. Worth knowing: when you have a fixed-aspect illustrated scene that needs to pin to one edge across device sizes, bottom-aligning the entire scene gives the most predictable hill/horizon behavior.

## feat/illustrations (2026-05-06)

Ports four placeholder-Ionicons-or-CSS-shaped illustrations to real Figma exports: Officer + Trooper characters in /pulled-over's review, the three onboarding-panel hero illustrations, the location-pin + car on /permissions, and a single composite backdrop for /index (Welcome) replacing the previous Vic + sun + CSS-hill stack and adding the missing clouds, wind, and border-cloud elements.

- **Figma MCP asset URLs return SVG bodies despite `Content-Type: text/html`.** First instinct was the URLs were broken (HTML head/length suggested a wrapping page). `curl -s <url> | head -c 500` showed real `<svg>...` content. The mismatch is just bad server-side content negotiation — pipe and inspect, don't trust headers. Saved hours of "why aren't these downloading right."
- **One composite screenshot beats reassembling positioned children.** Welcome's "Visuals" parent (825:3163) contains a vic + sun + hill + 7 clouds + 3 winds + border-cloud at specific x/y offsets. Trying to reproduce all that absolute positioning faithfully in RN would have been a bug-magnet (every cloud's pixel offset to maintain). Instead, requesting a screenshot of the parent gave a single 390×846 PNG that became the entire Welcome backdrop. The content (title, terms, buttons) overlays via SafeAreaView. One image, zero positioning math, exact Figma fidelity. Same trick works for any frame with many absolutely-positioned decorative elements.
- **`sips --cropOffset Y X --cropToHeightWidth H W` — Y first, X second.** First crop attempt got mostly empty white because I passed `0 369` (treated as Y=0, X=369 → crops from x=369 onward, basically off-image). Fixed by swapping to `369 0`. Even after fixing the order, sips silently kept the source's full dimensions on output (output was 390×844 instead of 390×475). Switched to PIL via `python3 -m pip install --user --quiet Pillow` + `img.crop((left, upper, right, lower))` which actually produced the cropped pixels. Worth knowing: when an image-tool's command "succeeds" but the output dimensions don't match what you asked for, the tool likely interpreted your args differently — read the output dimensions, not the exit code.
- **Crop screenshots once, render with `aspectRatio` in RN.** Onboarding panels' illustrations were cropped to 390×351 from the Figma panel screenshots. In RN we use `aspectRatio: 390/351` plus `width: <screenWidth>` so the image scales proportionally on Pro Max devices (430-wide) without distortion. Don't hardcode `height: 351` — it breaks on wider devices. The aspectRatio-driven height pattern is the responsive default for any fixed-aspect image asset.
- **PNG export resolution is generous; don't worry about retina.** Officer + Trooper PNGs came back at 1384×2186 / 1384×2361 from Figma despite rendering at 100×157 / 100×171pt. Far over even @3x retina (300×471 max needed). `resizeMode: 'contain'` handles the downscale crisply on any device pixel ratio. Lesson: don't pre-scale Figma exports to "the right" pt size; let RN do the per-device math against an oversized source.
- **Layered SVG overlays positioned via percentage `inset` need pixel calculation in RN.** Trooper's hat badge was authored in Figma as a separate SVG positioned at `inset-[20.99%_43.22%_68.99%_43.23%]` within the 120×172 wrapper. In RN we don't have percentage `top/right/bottom/left` for absolute positioning the same way, so I converted to pixels: `top: 36 (= 20.99% × 172), left: 52 (= 43.23% × 120)`. Pre-compute these against the wrapper's known dimensions; don't try to use `top: '20.99%'` — RN's behavior with percentage absolute insets is inconsistent across versions.
- **Removing CSS-shaped placeholders is a real cleanup.** Welcome's hill was a `View` with `borderTopLeftRadius: 600` + huge negative `left/right` to fake a curve — a hack that worked for v0 but read as obvious approximation against the rest of the brand. Replacing with the real Figma-authored hill curve (now part of the composite backdrop) made the screen feel intentionally designed instead of "we'll fix this later." Worth noting for any other CSS-approximated illustrations in the codebase: they're flagged in CLAUDE.md's "Polish/smaller gaps" section, and each one is a quick win to swap.
- **Defer the user-car glyph until the asset exists.** CLAUDE.md flags a custom user-car SVG that the user is making themselves (variant of the trusted-friend pin). It's not in Figma, so this branch can't pull it. Skipped on this PR; remains a one-tile follow-up commit when `assets/illustrations/user-car.svg` lands. Lesson: when an illustration audit's scope includes "asset to be created," explicitly skip it on the porting PR rather than placing a proxy that has to be replaced again later.

## feat/recordings-list (2026-05-06)

Builds the audio library for /pulled-over's safety captures: `lib/api/recordings.ts` adapter, `useRecordings` hook, `/recordings` screen with inline playback + delete, /pulled-over auto-saving on dismiss. Plus a mid-stop "Add a contact" recovery affordance for users who skipped trusted-contact onboarding, and a defensive name-derivation fix for iOS contacts that return `name: undefined`.

- **expo-file-system v19 is class-based now.** First pass used `FileSystem.documentDirectory` + `FileSystem.copyAsync` (the v18 procedural API); type-check failed because those exports are gone. v19 uses `new Directory(Paths.document, 'recordings')`, `new File(...)`, `file.copy(destFile)`, `file.delete()` — and most ops are *synchronous*. Async-to-sync is rare in JS migrations; worth knowing because every "wait, why isn't this returning a promise" instinct is wrong here.
- **Async work in unmount cleanups races the host hook's own teardown.** First save attempt did `await recorder.stop()` inside a `useEffect(() => () => {...})` cleanup. By the time the await resolved, `useAudioRecorder`'s own cleanup had run and disposed the native shared object — accessing `recorder.uri` threw `NativeSharedObjectNotFoundException`. Lesson: never *await* cross-hook resources from inside an unmount cleanup. The cleanup is allowed to run, but you don't control when other hooks' cleanups run relative to yours.
- **`usePreventRemove` > `navigation.addListener('beforeRemove')` for native-stack.** beforeRemove + preventDefault works on JS-stack but in native-stack the gesture dismiss removes the screen natively before JS can hold it back — you get a "screen was removed natively but didn't get removed from JS state" warning. usePreventRemove (from `@react-navigation/native`) is the supported pattern for this case. It also takes a boolean gate so you can flip it off after the work completes and re-dispatch the original action without re-triggering the prevent.
- **Always normalize at the adapter boundary; don't trust source SDKs to give you string-typed strings.** iOS's expo-contacts returned a Contact with `name: undefined` (only firstName/lastName were set), and `useTrustedContact.pickContact` passed it straight to `setTrustedContact({ name: picked.name, ... })`. TypeScript's `name: string` was satisfied in the call site (typed as `Contact['name']` which is optional) but the runtime stored undefined. `deriveContactName(name, firstName, lastName, phoneNumber)` now derives a real string before persistence. Worth knowing: SDK-typed-as-optional fields *will* be undefined for your edge-case users; build the fallback chain at the adapter, not the UI.
- **Mid-stress recovery affordances earn their keep even if rare.** The "no trusted contact set" state on /pulled-over previously rendered "?" initials + "No trusted contact set" + disabled Call/Text — a literal dead end at the worst moment. Replacing the avatar block with a tappable "Add a contact" affordance (UserPlus glyph, no pulse — pulsing on an empty avatar would lie about a connection) lets a user who skipped onboarding recover even mid-stop. Compromise: yes, opening an iOS contact picker during a stop is suboptimal. But "out of luck" is a much worse failure mode than "extra friction." Lesson: when shipping a flow that depends on prior setup, audit every "user skipped that setup" path and at minimum offer a recovery affordance. Hiding the feature behind onboarding alone is a bug magnet.
- **Defensive UI fallbacks pay off when data shape changes mid-development.** Stored contacts saved with `name: undefined` don't disappear when the adapter learns to derive names — they sit in AsyncStorage until cleared. ContactView's `contact?.name?.trim() || contact?.phoneNumber || NO_CONTACT_NAME` chain handles all three cases (real name, broken stored contact, no contact) without stranding the user on a contact they can't re-pick. Worth knowing: when you change a data-shape contract, the UI defends against the *old* shape until users churn through; pure adapter-level fixes leave existing-data users stuck.
- **Recordings library = artifact of safety flow, not top-level setting.** First instinct put Recordings as its own row in /menu's settings list. User pushed back: it's a safety-flow artifact, not a global preference, so it belongs under Safety Settings next to Trusted Contact. Lesson on info architecture: list a thing where its *origin* lives, not where the user might first look. /recordings exists *because* of /pulled-over; surfacing it under Safety keeps that lineage clear.
- **`useRecordings()` is per-instance state, not shared.** Each call to the hook creates its own `useState` cell. /pulled-over's instance saves a recording → its local state updates → its parent (about to unmount) doesn't care. /recordings's *separate* instance refetches on next mount (expo-router stack remounts on re-visit), so it sees the new entry. Worth knowing: this works *because* of stack-based remounting; if /recordings ever stays mounted (tabs, persistent route), we'd need either context-shared state or a focus refetch. Document the assumption (mount = fresh fetch) so the next refactor doesn't quietly break it.

## feat/menu-hub (2026-05-06)

Third "make it real" PR. The Settings spine that hosts secondary surfaces — `/menu` route pushed from /home's avatar button, hero header with car-icon identity glyph, trusted-contact edit, sign out. Sets the visual register for Recordings + Recent Trips when they arrive.

- **Asking for design input mid-build is sometimes the right move.** Started building /menu with iOS-Settings conventions (gray background, all-caps section labels, red Sign out). Halfway through, the user flagged they wanted to be more collaborative since there was no Figma. Surfacing the eight design decisions I'd already made — and which leans I had on each — produced a tighter design conversation than just shipping my first guess. Lesson: when extrapolating without a reference, *show the calls you're making* before completing the build, not after. The user gets to redirect cheaply; we both end up with a design we agreed on instead of one we have to revisit.
- **Brand register beats system convention when they conflict.** iOS Settings uses gray + uppercase tracked-out section labels + red destructive text. Fresh Greens' established register is wiltedgreen + Title1Emphasized + reserved-color rules where red = safety signal (not destructive action). Trying to match iOS would have made /menu read as a stranger room compared to every other auth/onboarding screen. Going wiltedgreen + Title1Emphasized + wiltedgreen-outline-pill Sign out kept the visual continuity. The user pushes from /home (white) to /menu (wiltedgreen) and into /trusted-contact-setup (wiltedgreen) without any color-temperature whiplash. Lesson: the established system trumps the OS convention when they collide. The OS can be referenced; the brand has to be honored.
- **One identity glyph across surfaces > "wherever the user is, show their data."** The trusted-friend pin on /home uses car iconography (per Figma). Extending the same car to the user's own avatar — at /home (28pt) AND /menu hero (80pt) — makes "user is a car-in-the-system" a coherent metaphor everywhere. Differentiated colors (freshgreen for trusted friend, fadedgreen for self) signal role within the same visual language. The first version of /menu used initials in a circle — functional but bureaucratic, no identity story. Cars-everywhere reads more like the app actually believes its own thesis ("drive like you know these roads").
- **A tsconfig `paths` mapping pays off twice.** First use was avoiding the type-check failure on phosphor's source TSX in /trusted-contact-setup. Second use is here in /menu and /home — same pattern, no extra config. The pattern is now portable to every future Phosphor icon use across the app. Worth knowing: when a third-party package's deep-import path is the right runtime answer but breaks type-check, tsconfig `paths` is the cleanest solution. Don't bury the suppression in `@ts-expect-error` per call site.
- **The dev Reset chip retired itself once Sign out shipped.** Removing one-off dev affordances when their permanent replacement lands is part of "real" — leaving them around as long-tail debug clutter is what makes a product feel like it has tools half-built. The chip lasted exactly the time between "Welcome auto-redirects so I need a sign-out somewhere" and "Settings exists, sign-out is in its real home." That's the right lifecycle for any `__DEV__` workaround: introduce when needed, remove when the real version ships.
- **Routing ambiguity is solved with explicit intent params, not stack inspection.** /trusted-contact-setup is reached from two places now: onboarding (where Continue should `replace('/home')`) and Settings (where Continue should `back()` to /menu). Trying to detect the entry point from the route stack would be brittle (what if the user deep-links someday?). The clean answer is a `from=settings` query param the entry-point route passes — explicit, debuggable, easy to extend with new entry points (`from=onboarding-resume`, etc). Lesson: when a screen serves multiple parent flows, let the parents declare themselves. Don't ask the screen to introspect.
- **Future direction documented in CLAUDE.md, not just in heads.** The Waze-flavored "tile grid + card-forward + identity-prominent" direction for /menu growth got written into CLAUDE.md so the next PR (Recordings or Recent Trips) starts from that direction instead of re-deriving from scratch. Lesson: when an aesthetic direction gets agreed on but isn't built yet, *write it down where the next PR will read it*. The conversation context where we agreed will be gone by then.
- **Designing without a Figma reference burns iterations.** First /menu commit shipped, user walked it on Expo Go, then we did several rounds of rework: hero scale, section label hierarchy, "Settings" page-title removal, accordion-pattern for the Zone toggle, row gap tightening, white-circle-vs-no-fill icon treatment, rectangular tile pivot, swipe-with-peek carousel, sign-out pinned to bottom, in-tile copy lifted from Figma Search Landing instead of generic placeholders. Each round was a real improvement, but each was a tank of iteration cost the design system couldn't pre-empt. Honest read for next time: when there's no Figma to anchor to, **expect 3–5 iterations on visual polish even after structure lands**. The collaboration only works if both sides know that going in.
- **`react-native-svg-transformer` makes Figma SVG → first-class component cheap.** Setup: install the dev dep, add 7 lines to `metro.config.js` (filter `assetExts`, add to `sourceExts`, set `babelTransformerPath`), declare `*.svg` module in a `.d.ts`. Result: `import FuelIcon from '...fuel.svg'` and the SVG is a real RN component that scales to any size. Worth knowing this is a 5-minute one-time setup. Once configured, every future custom illustration is `import` away — no more juggling `@1x`/`@2x`/`@3x` PNGs or fighting Image's resize math. The 32×32 PNG hold-over felt soft at 48pt; the same SVG looks crisp at any size.
- **Pinned-to-bottom layout = put the pinned thing OUTSIDE the ScrollView.** First /menu version had Sign out as the last child *inside* the ScrollView, which means it sat right under the last visible row and didn't get pushed to the bottom of the screen. Fix: ScrollView gets `flex: 1` (fills the space between header and pinned bottom), Sign out is a sibling of the ScrollView underneath, SafeAreaView's bottom edge handles the inset. When the carousel needed the same treatment, same pattern applied — pinned-to-bottom things live OUTSIDE the scrollable content. The tell that you're doing it wrong: the pinned thing's position depends on how much content is above it.
- **Subtitle copy from a real Figma frame > generic placeholder.** Original carousel tiles read "Set up" as the value line. After lifting the Search Landing's Fuel-section subtitle ("Add your car's model and fuel for refuel reminders") and writing the Notifications subtitle in the same register, the tiles felt purposeful instead of stub-y. Lesson: if the design system already has copy for adjacent surfaces, use that voice/register before inventing. The tone is part of the design, not just the layout.
- **A `Preferences` adapter scales better than per-feature constants.** `SHOW_ZONES` started as a `const` in home.tsx for thesis screenshots. As soon as it became a real user-visible toggle, it needed to live in storage with a typed shape that other prefs can join (theme, auto-record, distance units, etc.). Built `lib/api/preferences.ts` + `hooks/usePreferences.ts` matching the user/trusted-contact adapter pattern. One storage key, one merged Preferences object, per-key setters. Adding a new preference is now a one-property change to the type plus a setter. Worth knowing for any "this seems like just a debug constant for now" moment — the path from constant to real preference is foreseeable; build the adapter at the second use, not the third.

## feat/trusted-contact-end-to-end (2026-05-06)

Second "make it real" PR after Apple Sign In. Adds the trusted-contact picker (iOS-native via `expo-contacts`), wires the pulled-over contact phase to read it, and turns Call/Text into real `Linking.openURL('tel:…')` / `sms:…` actions. Also moves mic permission from mid-stress (during /pulled-over) to calm onboarding.

- **`presentContactPickerAsync()` is the right pick over `getContactsAsync` for v1.** The OS-native picker doesn't require the Contacts permission — the user picks one contact, only that contact comes back. We get a real native UX (familiar iOS picker, same as iMessage/Phone use), no permission dialog, no "show all contacts in our own UI" rabbit hole. Picker-style flows beat permission-then-list flows when the data scope is "one item I'm choosing right now."
- **Adapter shape stayed identical to user.ts.** Same `getX / setX / clearX` async surface, same AsyncStorage backing, same backend-swap-point comment. The third adapter using this pattern (zones / community-reports / user / trusted-contact = four now) means it's a real codebase convention, not a one-off. Future identity-style adapters (recordings, recent trips) should slot into the same shape.
- **Store only what the safety flow needs.** Contacts on iOS can be huge — addresses, social profiles, photos, all the postal labels. Caching the full Contact would be both privacy-sloppy and storage-wasteful. We extract `id`, `name`, `initials` (derived at save), `phoneNumber` (primary or first), `setAt` and persist that. The OS contact remains the source-of-truth; we cache the *projection* the app actually uses.
- **Fallbacks across denial paths matter.** Three places needed graceful degradation:
  - Skip during onboarding → no trusted contact → `/pulled-over` Call/Text buttons render *visible-but-disabled* (opacity 0.4, accessibilityState disabled, no-op handlers). Not hidden — hiding implies the feature doesn't exist; disabled implies "you can use this once you set it up."
  - Mic permission denied during onboarding → recording metering is undefined → waveform stays at flat baseline (already shipped behavior in audit-4's recording work; just inherits the fallback).
  - Picked contact has no phone number → `pickContact` throws a typed error caught in setup screen → user sees "Pick a different contact." rather than a silent failure.
- **Permission timing is part of UX.** Mic was originally requested during /pulled-over's guidance phase — the *worst* moment to interrupt with a system dialog. Moving the request to /permissions during calm onboarding lets the user grant in advance; the safety flow stays silent about it. Lesson: any permission that affects a critical-moment feature should be requested at a non-critical moment. If your app needs camera-during-emergency, ask for camera at signup, not at the emergency.
- **`tel:` / `sms:` URI schemes are platform-agnostic and reliable.** No platform-specific code needed; `Linking.openURL('tel:+1...')` works on iOS and Android. The number's format barely matters — both accept formatted (`(212) 555-0123`) and unformatted (`2125550123`). Worth knowing this isn't a fragile area; the brittle thing in real-call wiring is *getting* the number, not *using* it.
- **"Set-and-forget" defers the editable-Settings problem.** Trusted contact is set during onboarding only; there's no "edit my trusted contact" flow yet. That's a deliberate Plan A scope decision (Settings is its own next PR). It works because thesis-demo users go through onboarding once. The lesson is granular: when a feature has a setup phase and a use phase, you can ship just the setup phase + use phase first, and defer the *edit* phase until you have user feedback on what edit affordances actually need to exist.
- **Permission asks back-to-back are OK on iOS.** Originally I worried about "two dialogs in a row" feeling intrusive at /permissions (location then mic). It actually reads fine — iOS treats them as separate, sequential prompts; the user understands each one. The key is they're both contextually justified by the same screen ("we need these for routing + safety recording"). Not lumping them into a single "grant everything" prompt.
- **Onboarding momentum > permission gating.** /permissions originally dead-ended at iOS Settings on denial — the user had to leave the app, toggle the permission, swipe back, and tap again. That's a stall in the middle of a one-time flow. Better: always advance after the prompts fire, regardless of grant/deny. The app degrades gracefully without either permission. Users who denied can grant later via system Settings; they don't need to grant *right now* to keep moving. Lesson: onboarding should never have a "you can't continue without this" wall unless the feature is genuinely useless without it.
- **Phosphor's barrel index breaks Metro at scale.** `import { UserPlus } from 'phosphor-react-native'` triggers Metro to bundle the barrel — which re-exports ~9000 icons. Any single icon's resolution failure (we hit `./icons/Bank` for unclear reasons) crashes the entire bundle. Fix: deep-import via `phosphor-react-native/src/icons/UserPlus`. Metro now bundles only the one icon. Side-effect: TypeScript follows the deep `.tsx` source instead of the barrel's `.d.ts` and starts type-checking phosphor's strict-incompatible internals (`className` on Svg). `skipLibCheck` doesn't help because it skips `.d.ts`, not `.tsx` from `node_modules`. Real fix: tsconfig `paths` mapping that redirects TS to phosphor's precompiled `.d.ts` while Metro continues using the source. Two-tool, two-paths solution: TS uses `lib/typescript/icons/*`, Metro uses `src/icons/*`. Worth knowing this gotcha before reaching for any icon library that ships a giant barrel.
- **Dev affordances belong on a reachable screen.** Wanted to test cold-start onboarding repeatedly without deleting the simulator each time. But Welcome auto-redirects signed-in users — there's no surface a logged-in tester can reach to sign out. Solution: a `__DEV__`-gated "Reset (dev)" chip on Home (the place signed-in users land). Stripped from production builds automatically by Metro. Lesson: every "reset" or "logout" affordance has to consider the bootstrap problem — what screen can the user in the BAD state actually see?

## feat/auth-apple-signin (2026-05-06)

First "make it real" PR after the audit. Wires Apple Sign In via `expo-apple-authentication`, adds the missing `/login` screen, and introduces the user-identity adapter (`lib/api/user.ts`) + reactive hook (`hooks/useUser.ts`).

- **Adapter pattern carries to identity.** `lib/api/user.ts` follows the same shape the zones / community-reports / routes adapters use — typed `User`, async public surface (`getStoredUser`, `setStoredUser`, `clearStoredUser`, `upsertUser`), AsyncStorage internals as the v1 backing store, with the backend-swap point clearly marked. Identity now flows through the same architectural register as everything else, which is the win: a future Supabase swap is a single-file change, not a cross-screen refactor. The thesis claim of a typed-adapter pipeline now holds for auth too, not just data.
- **Apple's first-sign-in-only behavior is a real architectural concern.** Apple returns `fullName` and `email` only on the user's *first* sign-in to an app. Returning sign-ins return only the stable `user` ID. If you naively persist what Apple gives you each time, returning users overwrite their cached display name with nulls. `upsertUser` solves this by merging — newest-wins, but `null` doesn't overwrite a real value. This is the kind of provider quirk that's easy to miss until a returning user shows up with their initials reading "?".
- **Routing decisions belong at the call site, not in the auth hook.** `useUser`'s `signInWithApple` returns the freshly-stored User and stops. The caller (`/get-started` vs `/login`) decides where to navigate post-sign-in — first-time → `/onboarding`, returning → `/home`, login screen always → `/home`. Hooks shouldn't have opinions about flow; they should have opinions about state. Keeping the hook flow-agnostic means it slots into Settings sign-out / re-auth later without rewiring.
- **First-time vs returning is checked from storage, not from Apple's response.** Apple's `signInAsync` doesn't tell you whether this is the user's first time on this app. `getStoredUser()` *before* the sign-in does — if there's already a user record, this is a returning sign-in. Simple, source-of-truth-y, doesn't depend on provider quirks.
- **Auto-redirect needs a `loading` guard.** Welcome's auto-redirect for signed-in users (`if (!loading && user) router.replace('/home')`) requires waiting on the AsyncStorage read. Without the guard, `user` is briefly `null` on cold start even when a user IS stored, and Welcome would either flash and bounce, or worse, leave a signed-in user staring at the splash. The pattern is: don't navigate on absence-of-information, only on confirmed-information.
- **Auth + login as one PR is the right granularity.** Splitting them would have meant Welcome → /login routing nowhere meaningful for a stretch, OR a half-built login screen sitting in code without a destination. Bundling the two means main always has a working flow — the user can sign up, sign in, return, and re-enter the app coherently from the moment this lands. The "next PR" pattern (this one's a foundation; trusted-contact picker + recordings list build on top) keeps each branch small and testable while never landing a half-feature.
- **Visual reuse held off on extraction.** /login is a near-clone of /get-started's layout but routes differently and has different copy. Resisting the urge to extract a shared `<AuthScreen />` component before there's a third use — applying the rule of three. When Settings ships with a sign-in surface, that'll be the third use, and *then* the shared component will know what its real shape needs to be.
- **`usesAppleSignIn: true` in app.json + the plugin install + the entitlement = three things that all have to land together.** Forgetting any one breaks the sign-in sheet at runtime in ways the dev hasn't seen since the previous Expo SDK migration. Worth a one-time mental note: every iOS-entitlement feature has this three-part dance.

## feat/routing-formula-zones (2026-05-06)

The remaining three thesis factors — police, wildlife, road conditions — land as OSM-fed zones through the existing pipeline. What we did, in plain terms:

- **The discriminated union earned its keep again.** Adding three new categories to the routing formula meant: extend the Overpass query union, add new tag dispatchers in the parser, add new entries in mock fallback. **No change** required to `pickWinner`'s public signature, no consumer changes in /home or /en-route, no scoring inner-loop rewrite. Discriminated `geometry: 'polygon' | 'polyline' | 'point'` made the geometry side trivial; adding optional `category: ZoneCategory` made per-source modulation possible without touching the type system everywhere else. Three new data sources, ~200 lines of net adapter additions, zero ripples.
- **Time modulation belongs in scoring, not in the zones adapter.** The dawn/dusk wildlife multiplier could've been baked into the zone (compute "is it dusk" at fetch time, return type='avoid' instead of 'caution'). Doing it in scoring is cleaner: zones describe *what's there*; scoring decides *what to do about it given the trip context*. Trip context (departureTime) lives at the call site of `pickWinner`, not at the time of fetching zones — and a route may be re-scored against the same zones for different scheduled departures (the future "Schedule for 7:38 AM" feature). Single source of zone truth, multiple scorings as needed.

Lesson: when extending an Overpass query, check whether the new tag families use way/node/both before assuming the existing parser shape covers them.
- **`departureTime` defaults to `new Date()` so adding the param wasn't a breaking change.** Existing call sites in /home and /en-route still call `pickWinner(rawRoutes, allZones)` with no third argument — they implicitly mean "leave now," which is what most trips are. - **Mock fallback grew with the categories.** Original mock was 3 polygons covering safe/caution/avoid. With the new categories shipping behind the same `SHOW_ZONES` debug toggle, the mock needed to demonstrate police/wildlife/road-condition zones too — otherwise the demo screenshot would be misleading when Overpass is unreachable. Six mock zones now, one per category. Mock fidelity is part of the demo experience, not a fallback afterthought.

- **`false` in a style array is a no-op.** `style={[styles.dot, isInactive && styles.dotInactive]}` evaluates to either `[styles.dot, styles.dotInactive]` or `[styles.dot, false]`. RN's array merger silently ignores the `false`. Cleanest conditional-style pattern.
- **`Array.from({ length: n }).map((_, i) => ...)`** is the canonical "render n elements" pattern when you don't have a real array of data. The underscore signals "we don't care about the value, only the index."
- **`justifyContent: 'space-between'` doesn't mean buttons are pinned independently.** When the top child grows, the distributed gap shrinks; the bottom child stays at the bottom but appears closer to the body. Not a bug — feature of how the flex distribution works. The fix when this matters is usually a missing illustration filling the middle, not a layout change.

## chore/typography-tokens (2026-05-03)

- **Spread + override is the canonical token consumption pattern.** Spread the token to inherit the contract (size, weight, letter spacing), then add overrides (color, alignment, decorations) below. Reads top-down as "what kind of text + what's special about this instance."
- **Pull a single property when nested Text inherits.** For inner `<Text>` inside an outer `<Text>`, RN inherits size/lineHeight/letterSpacing automatically — only override the property that differs (e.g. `fontWeight: typography.footnoteEmphasized.fontWeight`). Spreading the whole token would re-apply already-inherited values redundantly.
- **A successful refactor has zero visual diff.** "Looks identical" is the success state. If something looks different post-refactor, the token or the consumer is wrong.

## feat/onboarding-1 (2026-05-03)

- **iOS system font is SF Pro by default** — leave `fontFamily` unset on `<Text>` and you get SF Pro automatically. Setting `fontFamily: 'SF Pro'` explicitly doesn't work; the system font is accessed by *not* naming it.
- **RN's `fontWeight` only accepts standard 100-step values** (100, 200, ..., 900). Figma's "Semibold" is technically PostScript weight 590, but RN maps Semibold to 600. Visually identical to the eye; spec-different on paper. Don't try to set 590 in RN — it'll snap to 600 anyway.

## feat/permissions (2026-05-03)

- **JSX nesting often needs to mirror Figma's group nesting.** A Figma group with `gap: 32` between visual-block and CTA isn't decorative — it's load-bearing structure. Flattening it into siblings of the SafeAreaView lost the relationship and put the CTA at the bottom instead of 32pt below the sub-instructions.
- **`alignItems: 'flex-start'` cascades through wrapper Views.** Each level inherits "be as small as your kids," which collapses long Text down to its intrinsic line width and visually swallows parent padding. Default `alignItems: 'stretch'` lets wrappers fill the cross-axis so Text wraps within the proper width.
- **The robust pattern: default `stretch` + `alignSelf` overrides on exceptions.** Don't flip the parent's `alignItems` and then compensate everywhere; let stretch be the default and add `alignSelf: 'flex-start'` (or `center`) only on the children that need different behavior.
- **Built-in `SafeAreaView` clobbers horizontal padding** because its inset application runs after React applies your styles and touches the same padding properties. Workaround: put `paddingHorizontal` on a parent View, leave only vertical concerns on SafeAreaView. Real fix: migrate to `react-native-safe-area-context` (next PR).
- **TEMP-wire pattern for testing in-progress routes.** When a screen exists but isn't reachable from the proper flow yet, temporarily wire an existing button to navigate there, with a clear `// TEMP:` comment so it's grep-able and obviously not permanent. Better than building a hidden dev menu just for one route.

## feat/screen-illustrations (2026-05-02)

- **`<Image>` needs explicit width AND height.** The `left: 0, right: 0` shorthand that implicitly widths a `<View>` doesn't reliably work on Image — RN can fall back to the asset's natural pixel size (huge, since 3x exports are 3× the design dimensions). Always set `width` explicitly.
- **`require('../path/to/file.png')` bundles a local asset at build time.** Different from `source={{ uri: 'https://...' }}` which fetches a remote URL at runtime. Metro reads `require()` calls statically and packs the file into the app bundle.
- **`resizeMode="contain"` fits the image inside its bounds preserving aspect ratio.** Other options: `cover` (fills, may crop), `stretch` (fills, may distort), `center` (no scaling). `contain` is almost always right for illustrations.
- **`transform: [{ translateX: N }, { translateY: M }]` shifts an element visually without affecting layout flow.** Negative Y = up (screen coords have y pointing down). Use for fine-tuning position without cascading into siblings.
- **JSX source order = paint order for overlapping absolute siblings.** Earlier in JSX = behind, later = in front. No `z-index` needed for sibling overlaps. Useful for masking via overlap (sun behind hill = clean rising-sun silhouette without a pre-clipped asset).
- **Centering an absolutely-positioned element:** `left: '50%', marginLeft: -<half-width>`. The `left: 50%` puts the *left edge* at center; the negative margin pulls the element back so its *center* sits on center. Same trick vertically with `top` + `marginTop`.
- **`accessible={false}` on decorative images** tells VoiceOver to skip them. Sun, clouds, atmospheric art = decorative; UI icons that convey meaning = `accessible={true}` with a label.
- **New asset directories sometimes need `npx expo start -c`** to be picked up by Metro's file watcher. Hot reload works for code changes but can miss brand-new directories.

## feat/get-started (2026-05-02)

- **`onPress={handler()}` runs at render time and is almost always wrong.** `onPress` wants a function, not the result of calling one. Three forms: `onPress={fn}` if no args, `onPress={() => fn(arg)}` if args, never `onPress={fn()}`.
- **Arrow function `() => expr` is shorthand for `function() { return expr }`.** Defines an anonymous function that runs `expr` when called.
- **`useRouter()` is a hook — call it at the top of the component**, not inside conditionals or loops. Hooks always start with `use`.
- **`router.push('/path')` matches a file at `app/path.tsx`.** That's the file-based routing magic — no manual route registration.
- **Pattern reuse from screen to screen is a trap.** Welcome had a curved hill; I copied the same View+borderRadius onto Get Started without checking the design — but Get Started's divider is *flat*. Look at the design first, name the shape, then decide whether to reuse. Anti-slop rule "match existing patterns" only applies when the new screen actually wants the existing pattern.
- **Name styles by what they are, not where they came from.** `hill` implies a curve; `ground` describes a flat lower section. Future-you reading the file shouldn't have to guess.

## feat/welcome (2026-05-01)

- **Git commits live in `.git/` locally — they're real before you push.** GitHub is just a hosted copy. `git push` is backup + share, not "make the commit count."
- **`git checkout -b` = create a branch *and* switch to it.** `-b` is `--branch`, the create flag.
- **`-u` on `git push` sets upstream tracking.** First push only; later pushes are just `git push`.
- **`as const` on a TS object literal** narrows the inferred types from `string` → exact literals. Combined with `keyof typeof`, that's how you get a union type of valid color names.
- **In RN, `borderRadius` clamps to half the element's width.** A 240 radius on a 390-wide View becomes 195 on each top corner — and two 195-radius quarter-circles meeting at the top-center give a tombstone dome, not a hill. Fix: extend the element past the screen edges + much larger radius. Only the gentle middle of the arc shows.
- **RN layout is bottom-anchored when actions are pinned to the bottom.** To move a sibling *up*, increase the gap *below* it (its `marginBottom`), not the space above it. Backwards from web instinct.
- **`StyleSheet` has no units.** Numbers are density-independent pixels; same physical size on iPhone SE and Pro Max.
- **`fontWeight` in RN is a string, not a number.** `'700'`, not `700`. Trips everyone up once.
- **`Text` can't sit directly inside a `View` as a string.** Always wrap in `<Text>`. Different from HTML.
- **Built-in `SafeAreaView` is the simpler version.** `react-native-safe-area-context` is the more capable replacement we'll swap in when the built-in misbehaves (landscape, side notches, custom inset positioning).
