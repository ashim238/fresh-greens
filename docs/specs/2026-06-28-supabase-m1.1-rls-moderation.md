# M1.1 — Supabase RLS + Community-Report Moderation

**Date:** 2026-06-28
**Status:** Spec (pre-build)
**Milestone:** M1.1 — Community cloud: stand up + harden (per `docs/ROADMAP.md`)
**Audience:** grant reviewer, future-me, any collaborator who joins the build

---

## Frame

The Fresh Greens community-report client (`lib/api/sources/community-cloud.ts`,
~181 LOC, gated by `isCommunityCloudConfigured()`) is already built. What this
spec covers is **the server-side hardening that must land before any real user
submits a report into a shared backend** — RLS policies, moderation surfaces,
the threat model, and the operational checklist to stand it up.

The thesis claim Fresh Greens makes — *whose safety knowledge counts when the
route is computed?* — answers the moderation question implicitly: the people
who participate are the people whose voices carry, so the system must protect
their participation from being weaponized against them. The Jacobs-thread
concern ("a biased cluster of reports redlines a neighborhood") goes live the
instant two devices share data. Hardening before users arrive is non-negotiable.

This spec is the artifact a grant reviewer would cite when asking *"How does
this app prevent weaponization?"* It is also the contract the next build
session implements against.

### The two-track design statement

The six report categories split cleanly:

- **Condition reports** (`lighting`, `hazard`, `incident`, `felt-unsafe`) —
  *negative-space safety signals*. A biased cluster here is the redlining
  attack: enough "felt-unsafe" reports in a neighborhood push routes around
  it, materially affecting which communities get served.

- **Place reports** (`felt-welcome`, `black-owned`) — *positive-space community
  signals*. A bad-faith report is reputational ("falsely claimed restaurant X
  is Black-owned"), not structural redlining.

The asymmetry is **intentional and load-bearing**: positive contributions stay
frictionless, accusatory contributions require accountability. Two-track is the
design statement, not a security afterthought.

## Decisions index

The 21 structural decisions this spec implements. Each row is a Q&A from the
grill session that produced this doc.

| # | Decision | Chosen |
|---|----------|--------|
| 1 | Track split | Two-track (condition vs place) |
| 2 | Condition auth model | Hard sign-in required |
| 3 | Auth method | Apple Sign-in default + phone-OTP escalation when abuse signals fire |
| 4 | Place auth | Anonymous + rate-limited |
| 5 | Anonymous device signal | Device-UUID (Keychain) + server-side IP-fingerprint log (composite) |
| 6 | Rate limits | Asymmetric: cond 3/24h+1/cluster, place 8/24h; cond soft-cap 5 → OTP gate; server-side IP-UUID alert ≥ 5 |
| 7 | User-side flagging | Anyone flags; 2 signed-in flags/24h → auto-hide, UNLESS both flags share IP or device-UUID (then queue for review) |
| 8 | Moderator access model | Role-based (`user_roles` table); `role = 'moderator'`; bootstrap = you |
| 9 | Moderator surface scope | Queue + adjudicate with investigation panels (submitter history, nearby reports, flagger breakdown); Restore / Remove (+ 7d device-UUID ban) |
| 10 | `community_reports` column additions | `auth_user_id`, `device_uuid`, `submitter_ip` (raw, server-only, 90-day retention), `is_verified_phone`, `hidden_at`, `hidden_reason`, `removed_at`, `place_type` (drift fix) |
| 11 | New tables | `user_roles`, `report_flags`, `device_bans`, `moderation_actions` audit log |
| 12 | `community_reports` SELECT | B++: public view with stripped server-only cols + per-category anonymity filter + `trust_tier` derived column ('verified'/'community'/'contributor'); shown on detail-card tap only, never on pin |
| 13 | `community_reports` INSERT | Policy + trigger split; distinguishable `ERRCODE`s for each block reason |
| 14 | `community_reports` UPDATE | Blocked; allow-list of `{submitted_by, photo_uri (attach/clear only)}` for submitter |
| 15 | `community_reports` DELETE | Soft-delete via RPC for both submitter and moderator; flags retained through deletion (no CASCADE); archive job deferred to v2 |
| 16 | RLS on 4 new tables + public window | Mod-only across the board + `moderation_actions_public` aggregate view; surfaced via a tiny external Edge Function page linked from the case study |
| 17 | Sign-in flow firing point | C+D: silent anonymous auth at launch + interactive Apple Sign-in at the Report-FAB entry point, with anon-session upgrade via `linkIdentity` |
| 18 | OTP escalation UX | Bottom-sheet ("Verify phone" / "Not now"); in-flight report drops on "Not now" |
| 19 | OTP provider | Supabase Auth built-in; note to upgrade to Twilio Verify if SIM-farm brigading emerges |
| 20 | Moderator route placement | Menu entry (role-gated render) + push notifications for queue events |
| 21 | Action confirmation | Restore = tap; Remove = hold (per-row); bulk Remove = multi-select + review modal + hold-to-confirm |

## Schema

### Changes to `community_reports`

**Existing columns** (do not modify):
`id, category_id, location, detail, sub_tag, place_name, google_place_id,
submitted_by, photo_uri, timestamp`

**Added columns** (Q10):

| Column | Type | Purpose |
|--------|------|---------|
| `auth_user_id` | `uuid REFERENCES auth.users(id)` | Apple/anon Supabase identity. NULL only impossible in practice (Q17 silent anon); the FK is the trust anchor. |
| `device_uuid` | `text NOT NULL` | Keychain-persisted device identity, sent as `x-device-uuid` header. Rate-limit + abuse-signal anchor. Server-only via RLS. |
| `submitter_ip` | `inet` | Server-recorded via `inet_client_addr()` in INSERT trigger. Raw IP, 90-day retention, moderator-only via RLS. |
| `is_verified_phone` | `boolean NOT NULL DEFAULT false` | TRUE if this submission cleared the OTP escalation gate. |
| `hidden_at` | `timestamptz` | Non-NULL = hidden from public view. Auto-hide or moderator action. |
| `hidden_reason` | `text` | `'flag-threshold'` / `'moderator-action'` / `'submitter-deleted'`. |
| `removed_at` | `timestamptz` | Soft-delete timestamp. Distinct from `hidden_at` (recoverable). |
| `place_type` | `text` | Fixes existing wire/client drift — `CommunityReport.placeType` exists client-side but was missing from the wire row. |

**Indexes**:


### New tables (Q11)

**`user_roles`** — moderator role registry:

```sql
CREATE TABLE user_roles (
  user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE,
  role text NOT NULL CHECK (role IN ('moderator')),
  granted_at timestamptz NOT NULL DEFAULT now(),
  granted_by uuid REFERENCES auth.users(id),
  PRIMARY KEY (user_id, role)
);
```

Bootstrap is a one-time SQL script run from the Supabase SQL editor (not via
the API). The first moderator (`granted_by = NULL`) is you.

**`report_flags`** — user-side flagging:

```sql
CREATE TABLE report_flags (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  report_id text NOT NULL REFERENCES community_reports(id),
  flagger_auth_user_id uuid REFERENCES auth.users(id) NOT NULL,
  flagger_device_uuid text NOT NULL,
  flagger_ip inet NOT NULL,
  reason text,
  reason_category text CHECK (reason_category IN
    ('spam', 'inaccurate', 'misleading', 'abusive', 'other')) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (report_id, flagger_device_uuid)
);
```

`flagger_auth_user_id` is non-nullable post-Q17 (silent anon means every user
has a uid). `flagger_ip` follows the same retention story as `submitter_ip`.

**`device_bans`** — Remove-action enforcement:

```sql
CREATE TABLE device_bans (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  device_uuid text NOT NULL,
  category_id text,                            -- NULL = global; else per-category
  banned_until timestamptz NOT NULL,
  reason text NOT NULL,
  banned_by uuid REFERENCES auth.users(id) NOT NULL,
  banned_at timestamptz NOT NULL DEFAULT now()
);
-- Plain composite index. `WHERE banned_until > now()` was rejected by
-- Postgres (predicate must be IMMUTABLE; `now()` is not). The rate-
-- limit trigger lookup `WHERE device_uuid = X AND banned_until > now()`
-- uses this composite index efficiently anyway; the partial-filter
-- was a micro-optimization, not load-bearing.
CREATE INDEX device_bans_active_idx
  ON device_bans (device_uuid, banned_until);
```

**`moderation_actions`** — audit log:

```sql
CREATE TABLE moderation_actions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  actor_user_id uuid REFERENCES auth.users(id) NOT NULL,
  target_report_id text NOT NULL,              -- not FK: target may be hard-purged later
  action text NOT NULL CHECK (action IN
    ('moderator-remove', 'moderator-restore', 'moderator-ban',
     'submitter-delete', 'correction')),
  notes text,
  occurred_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX moderation_actions_target_idx
  ON moderation_actions (target_report_id, occurred_at DESC);
CREATE INDEX moderation_actions_actor_idx
  ON moderation_actions (actor_user_id, occurred_at DESC);
```

UPDATE and DELETE on `moderation_actions` are **blocked by RLS even for
moderators** — corrections are new INSERT rows with `action = 'correction'`.
Postgres-enforced immutability is the accountability claim's spine.

### Public views (Q12, Q16)

**`community_reports_public`** — the wire shape seen by `anon` and
`authenticated` roles. Strips server-only columns, enforces per-category
anonymity, derives `trust_tier`:

```sql
CREATE VIEW community_reports_public AS
SELECT
  id, category_id, location, detail, sub_tag, place_name,
  place_type, google_place_id, photo_uri, timestamp,
  CASE
    WHEN category_id IN ('lighting','hazard','incident','felt-unsafe')
    THEN NULL
    ELSE submitted_by
  END AS submitted_by,
  -- B++ trust-tier signal (rendered on detail-card tap only):
  --   'verified'   = OTP-cleared
  --   'community'  = Apple Sign-in (condition default)
  --   'contributor'= Anonymous device-UUID (place default)
  CASE
    WHEN is_verified_phone THEN 'verified'
    WHEN auth_user_id IS NOT NULL
         AND EXISTS (
           SELECT 1 FROM auth.identities
           WHERE user_id = community_reports.auth_user_id
             AND provider = 'apple'
         ) THEN 'community'
    ELSE 'contributor'
  END AS trust_tier
FROM community_reports
WHERE hidden_at IS NULL AND removed_at IS NULL;

GRANT SELECT ON community_reports_public TO anon, authenticated;
```

**`community_reports_moderation`** — moderator-only full view (every column,
including server-only):

```sql
CREATE VIEW community_reports_moderation AS
SELECT * FROM community_reports;
-- RLS on the base table restricts access; see RLS section below.
```

**`moderation_actions_public`** — aggregate transparency view (Q16):

```sql
CREATE VIEW moderation_actions_public AS
SELECT
  action,
  date_trunc('day', occurred_at) AS day,
  count(*) AS action_count
FROM moderation_actions
GROUP BY action, date_trunc('day', occurred_at);

GRANT SELECT ON moderation_actions_public TO anon, authenticated;
```

No user IDs in the output. Surfaced via a Supabase Edge Function returning JSON
to a single static HTML page on the portfolio domain, linked from the
case-study "moderation" section.

## RLS policies

### `community_reports`

**Enable RLS, revoke direct table access from public roles:**

```sql
ALTER TABLE community_reports ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON community_reports FROM anon, authenticated;
```

**SELECT** — public reads go through the view; moderators read the base table:

```sql
CREATE POLICY community_reports_moderator_select ON community_reports
  FOR SELECT
  USING (EXISTS (
    SELECT 1 FROM user_roles
    WHERE user_id = auth.uid() AND role = 'moderator'
  ));
```

**INSERT** — boolean policy + procedural trigger (Q13):

```sql
CREATE POLICY community_reports_insert ON community_reports
  FOR INSERT
  WITH CHECK (
    -- Always require an authenticated session (Q17 silent anon guarantees this)
    auth.uid() IS NOT NULL
    AND auth_user_id = auth.uid()
    -- Condition track additionally requires Apple identity
    AND CASE
      WHEN category_id IN ('lighting','hazard','incident','felt-unsafe')
        THEN EXISTS (
          SELECT 1 FROM auth.identities
          WHERE user_id = auth.uid() AND provider = 'apple'
        )
      ELSE true
    END
  );

CREATE FUNCTION enforce_report_insert() RETURNS trigger AS $$
DECLARE
  recent_count int;
  cluster_count int;
BEGIN
  -- Required server-recorded fields
  NEW.submitter_ip := inet_client_addr();
  IF NEW.device_uuid IS NULL THEN
    RAISE EXCEPTION 'device_uuid required' USING ERRCODE = '23502';
  END IF;

  -- Active ban check (per-category if scoped, global if not)
  IF EXISTS (
    SELECT 1 FROM device_bans
    WHERE device_uuid = NEW.device_uuid
      AND banned_until > now()
      AND (category_id IS NULL OR category_id = NEW.category_id)
  ) THEN
    RAISE EXCEPTION 'device banned for this category' USING ERRCODE = 'P0001';
  END IF;

  -- Rate-limit: per device / 24h
  SELECT count(*) INTO recent_count
    FROM community_reports
   WHERE device_uuid = NEW.device_uuid
     AND timestamp > extract(epoch FROM now() - interval '24 hours') * 1000;

  -- Condition: 3/24h, soft-cap 5 → must have is_verified_phone
  IF NEW.category_id IN ('lighting','hazard','incident','felt-unsafe') THEN
    IF recent_count >= 5 AND NOT NEW.is_verified_phone THEN
      RAISE EXCEPTION 'otp escalation required' USING ERRCODE = 'P0002';
    END IF;
    IF recent_count >= 3 THEN
      RAISE EXCEPTION 'rate limit exceeded' USING ERRCODE = 'P0003';
    END IF;
  ELSE
    -- Place: 8/24h
    IF recent_count >= 8 THEN
      RAISE EXCEPTION 'rate limit exceeded' USING ERRCODE = 'P0003';
    END IF;
  END IF;

  -- Spatial cluster (condition only): max 1 per ~50m / 24h
  IF NEW.category_id IN ('lighting','hazard','incident','felt-unsafe') THEN
    SELECT count(*) INTO cluster_count
      FROM community_reports
     WHERE device_uuid = NEW.device_uuid
       AND timestamp > extract(epoch FROM now() - interval '24 hours') * 1000
       AND earth_distance(
             ll_to_earth(
               (location->>'latitude')::float,
               (location->>'longitude')::float),
             ll_to_earth(
               (NEW.location->>'latitude')::float,
               (NEW.location->>'longitude')::float)
           ) <= 50;
    IF cluster_count >= 1 THEN
      RAISE EXCEPTION 'cluster limit exceeded' USING ERRCODE = 'P0004';
    END IF;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER community_reports_insert_trg
  BEFORE INSERT ON community_reports
  FOR EACH ROW EXECUTE FUNCTION enforce_report_insert();
```

**Error codes:**

| ERRCODE | Meaning | Client mapping |
|---------|---------|----------------|
| `P0001` | Active device ban for this category | Inline error: "This device can't post to this category for now." |
| `P0002` | Soft-cap reached, OTP escalation required | Bottom-sheet (Q18 B) |
| `P0003` | Rate limit (3/24h cond or 8/24h place) | Inline error: "You've reached your daily reporting limit." |
| `P0004` | Spatial cluster cap (1 per ~50m / 24h cond) | Inline error: "You've already reported near this spot today." |
| `P0005` | Disallowed UPDATE column | "Reports can't be edited after posting." |
| `P0006` | Photo swap attempted (must clear first) | "Add or remove a photo, but not swap one." |
| `P0007` | State column write attempted by non-moderator | "Moderator-only action." |

**UPDATE** — submitter can edit attribution-only fields (Q14):

```sql
CREATE POLICY community_reports_attribution_update ON community_reports
  FOR UPDATE TO authenticated
  USING (auth.uid() = auth_user_id)
  WITH CHECK (auth.uid() = auth_user_id);

CREATE FUNCTION enforce_attribution_only_update() RETURNS trigger AS $$
BEGIN
  -- Reject any change to content/state columns
  IF NEW.category_id IS DISTINCT FROM OLD.category_id
    OR NEW.location IS DISTINCT FROM OLD.location
    OR NEW.detail IS DISTINCT FROM OLD.detail
    OR NEW.sub_tag IS DISTINCT FROM OLD.sub_tag
    OR NEW.place_name IS DISTINCT FROM OLD.place_name
    OR NEW.google_place_id IS DISTINCT FROM OLD.google_place_id
    OR NEW.place_type IS DISTINCT FROM OLD.place_type
    OR NEW.timestamp IS DISTINCT FROM OLD.timestamp
    OR NEW.device_uuid IS DISTINCT FROM OLD.device_uuid
    OR NEW.auth_user_id IS DISTINCT FROM OLD.auth_user_id
    OR NEW.is_verified_phone IS DISTINCT FROM OLD.is_verified_phone
  THEN
    RAISE EXCEPTION 'only attribution columns are user-editable'
      USING ERRCODE = 'P0005';
  END IF;

  -- photo_uri: attach (NULL→value) or clear (value→NULL), never swap
  IF NEW.photo_uri IS DISTINCT FROM OLD.photo_uri
     AND OLD.photo_uri IS NOT NULL AND NEW.photo_uri IS NOT NULL THEN
    RAISE EXCEPTION 'photo can be added or removed, not swapped'
      USING ERRCODE = 'P0006';
  END IF;

  -- State columns untouchable
  IF NEW.hidden_at IS DISTINCT FROM OLD.hidden_at
    OR NEW.removed_at IS DISTINCT FROM OLD.removed_at
    OR NEW.hidden_reason IS DISTINCT FROM OLD.hidden_reason
  THEN
    RAISE EXCEPTION 'state columns are moderator-only'
      USING ERRCODE = 'P0007';
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER community_reports_update_trg
  BEFORE UPDATE ON community_reports
  FOR EACH ROW EXECUTE FUNCTION enforce_attribution_only_update();
```

**DELETE** — blocked at the table level; soft-delete RPCs only (Q15):

```sql
REVOKE DELETE ON community_reports FROM anon, authenticated;

CREATE FUNCTION submitter_delete_report(p_report_id text) RETURNS void AS $$
BEGIN
  UPDATE community_reports
     SET removed_at = now(),
         hidden_reason = 'submitter-deleted'
   WHERE id = p_report_id
     AND auth_user_id = auth.uid()
     AND removed_at IS NULL;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'not your report, or already removed';
  END IF;
  INSERT INTO moderation_actions (actor_user_id, target_report_id, action)
    VALUES (auth.uid(), p_report_id, 'submitter-delete');
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE FUNCTION moderator_remove_report(p_report_id text, p_reason text)
  RETURNS void AS $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM user_roles
    WHERE user_id = auth.uid() AND role = 'moderator'
  ) THEN
    RAISE EXCEPTION 'not a moderator';
  END IF;
  UPDATE community_reports
     SET removed_at = now(),
         hidden_reason = 'moderator-action'
   WHERE id = p_report_id AND removed_at IS NULL;
  INSERT INTO moderation_actions (actor_user_id, target_report_id, action, notes)
    VALUES (auth.uid(), p_report_id, 'moderator-remove', p_reason);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE FUNCTION moderator_restore_report(p_report_id text, p_reason text)
  RETURNS void AS $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM user_roles
    WHERE user_id = auth.uid() AND role = 'moderator'
  ) THEN
    RAISE EXCEPTION 'not a moderator';
  END IF;
  UPDATE community_reports
     SET removed_at = NULL,
         hidden_at = NULL,
         hidden_reason = NULL
   WHERE id = p_report_id;
  INSERT INTO moderation_actions (actor_user_id, target_report_id, action, notes)
    VALUES (auth.uid(), p_report_id, 'moderator-restore', p_reason);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

The auto-hide-on-threshold trigger fires after a flag insert, checking the
Q7 anti-brigade rule (same IP or device-UUID → queue instead of auto-hide):

```sql
CREATE FUNCTION check_flag_auto_hide() RETURNS trigger AS $$
DECLARE
  signed_flag_count int;
  distinct_ip_count int;
  distinct_device_count int;
BEGIN
  -- Count signed-in flags on this report in last 24h
  SELECT count(*),
         count(DISTINCT flagger_ip),
         count(DISTINCT flagger_device_uuid)
    INTO signed_flag_count, distinct_ip_count, distinct_device_count
    FROM report_flags
   WHERE report_id = NEW.report_id
     AND created_at > now() - interval '24 hours';

  -- 2+ signed-in flags with at least 2 distinct IPs AND 2 distinct devices
  -- → auto-hide. Anti-brigade: same IP or same device collapses to 1 distinct.
  IF signed_flag_count >= 2
     AND distinct_ip_count >= 2
     AND distinct_device_count >= 2 THEN
    UPDATE community_reports
       SET hidden_at = now(),
           hidden_reason = 'flag-threshold'
     WHERE id = NEW.report_id AND hidden_at IS NULL;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER report_flags_after_insert
  AFTER INSERT ON report_flags
  FOR EACH ROW EXECUTE FUNCTION check_flag_auto_hide();
```

### IP retention job

```sql
-- Run nightly: null IPs older than 90 days
CREATE FUNCTION purge_old_ips() RETURNS void AS $$
BEGIN
  UPDATE community_reports
     SET submitter_ip = NULL
   WHERE submitter_ip IS NOT NULL
     AND timestamp < extract(epoch FROM now() - interval '90 days') * 1000;

  UPDATE report_flags
     SET flagger_ip = NULL
   WHERE flagger_ip IS NOT NULL
     AND created_at < now() - interval '90 days';
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Schedule via pg_cron (Supabase extension)
SELECT cron.schedule('purge-old-ips', '0 3 * * *', 'SELECT purge_old_ips()');
```

## Client API additions

### Auth surfaces (Q17, Q18, Q25, Q26)

**Silent anonymous at launch.** Add to `app/_layout.tsx` startup:

```typescript
// On every cold start, ensure an anon session exists.
// linkIdentity later upgrades it to Apple without losing the session id.
useEffect(() => {
  void (async () => {
    const { data } = await supabase.auth.getSession();
    if (!data.session) {
      await supabase.auth.signInAnonymously();
    }
  })();
}, []);
```

**Apple Sign-in at Report-FAB entry-point.** The flow is intercepted in the
existing Report-FAB tap handler — before pushing to `/report`, check whether
the current session has an Apple identity; if not, present the entry-point
sheet (new component, `<AppleSignInEntrySheet>`). On success: call
`supabase.auth.signInWithIdToken({ provider: 'apple', token })` which
`linkIdentity`s the anon session up to Apple. Sheet copy:

> **Sign in to submit reports**
> Your identity keeps the safety map accountable. We use Apple Sign-in so
> your phone number stays private.
>
> [Sign in with Apple]   [Not now]

**OTP escalation at soft-cap.** When `pushCommunityReportToCloud` catches a
`P0002` error: present `<OtpEscalationSheet>`. Copy:

> **Verify your phone to keep reporting**
> You've submitted 5 reports in the last day. To submit more, verify a
> phone number — this helps keep the safety map accountable.
>
> [Verify phone]   [Not now]

On `Not now`: in-flight report drops (Q18); user can return tomorrow once
the 24h window rolls.

### Device-UUID generation (Q22)

New module `lib/device-id.ts`:

```typescript
import * as SecureStore from 'expo-secure-store';
import { randomUUID } from 'expo-crypto';

const KEY = 'fresh-greens.device-uuid.v1';
let cached: string | null = null;

export async function getDeviceUuid(): Promise<string> {
  if (cached) return cached;
  const stored = await SecureStore.getItemAsync(KEY);
  if (stored) {
    cached = stored;
    return stored;
  }
  const fresh = randomUUID();
  await SecureStore.setItemAsync(KEY, fresh);
  cached = fresh;
  return fresh;
}
```

Read at app startup, included as `x-device-uuid` header on every Supabase
REST/RPC call via a wrapper in `community-cloud.ts`.

### Error-code → user-copy map (Q23)

Extend `lib/error-message.ts` with `domain: 'community-report'` namespace.
The seven `P-` codes map to the inline copy listed in the RLS error-codes
table above. `P0002` is special — it doesn't map to inline copy; it triggers
the OTP escalation sheet flow.

### Sync queue + auth (Q24)

Extend the existing `SYNC_QUEUE_KEY` shape to include the auth tier required
at flush time:

```typescript
type QueuedReport = {
  report: CommunityReport;
  requiredTier: 'anon' | 'apple' | 'otp-verified';
};
```

`flushCommunityReportSyncQueue` checks the current session against
`requiredTier` before flushing each item; mismatches stay queued or trigger
the appropriate auth challenge.

### Push notifications (Q27)

**Server side** — Supabase Edge Function triggered by Postgres triggers on
`report_flags` (after insert) and `community_reports` (after update where
`hidden_at` transitioned NULL → NOT NULL). The function:

1. Looks up moderator push tokens from a new `moderator_devices` table.
2. Applies the per-report 30-minute debounce.
3. Sends via Expo's push API (which wraps APNs).

**`moderator_devices` table** (Q27):

```sql
CREATE TABLE moderator_devices (
  user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE,
  expo_push_token text NOT NULL,
  registered_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, expo_push_token)
);

ALTER TABLE moderator_devices ENABLE ROW LEVEL SECURITY;

-- Only a moderator can register their own device
CREATE POLICY moderator_devices_self_register ON moderator_devices
  FOR INSERT TO authenticated
  WITH CHECK (
    user_id = auth.uid()
    AND EXISTS (
      SELECT 1 FROM user_roles
      WHERE user_id = auth.uid() AND role = 'moderator'
    )
  );

CREATE POLICY moderator_devices_self_read ON moderator_devices
  FOR SELECT TO authenticated
  USING (user_id = auth.uid());
```

**Notification payload** — minimal PII:

```json
{
  "to": "<expo_push_token>",
  "title": "New report flagged for review",
  "body": "Tap to open the moderation queue.",
  "data": { "report_id": "<uuid>", "screen": "/moderation/[id]" }
}
```

Never includes report content, location, or submitter identity in the
notification text.

## Moderator UI IA (Q28)

### Route placement

`/moderation` — gated route. Menu entry rendered only when
`user_roles` has `(auth.uid(), 'moderator')`. Push notifications deep-link
to `/moderation/[report_id]`.

### Queue layout

Vertical scroll of report cards. Sort: auto-hidden first, then flag-count
desc, then timestamp desc.

Each row:

```
┌─────────────────────────────────────────────┐
│ [category glyph]  Wintzell's Oyster House   │
│                   12 min ago                │
│                                             │
│ [2 flags]  [verified]  [auto-hidden]        │
│                                    [chevron]│
└─────────────────────────────────────────────┘
```

Tap chevron → row expands inline with three investigation panels:
- **Submitter history** — last 10 reports from this `auth_user_id` and from
  this `device_uuid` (independent lists; the divergence between them is the
  signal).
- **Nearby reports** — map preview centered on the report, showing all
  reports within ~500m + their state badges. Spot the cluster.
- **Flagger breakdown** — count of anonymous vs signed-in flags, count of
  distinct IPs, count of distinct device-UUIDs, with the anti-brigade
  threshold prominently displayed (e.g. "2 of 2 distinct IPs required to
  auto-hide — met").

Inline expand (not modal) per Q28 — moderators compare panels across rows
quickly.

### Actions (Q21)

- **Restore** — tap fires. Toast + Undo (5s).
- **Remove** — hold-to-confirm (800ms ring, same as SOS pattern). Writes
  `moderation_actions` row, soft-deletes report, inserts a 7-day
  `device_bans` row for the submitter's `device_uuid` scoped to the report's
  `category_id`.

### Bulk mode (Q21 → C extension)

Header "Select" button → checkboxes appear on rows, toolbar swaps to
`Cancel / Remove (N) / Restore (N)`. Tapping `Remove (N)` opens a modal
listing the N selected reports as cards; the modal contains the
hold-to-confirm gesture. On confirm: N transactions in one batch, N audit
rows (bulkness is implicit — same actor + millisecond-tight timestamps).

VoiceOver bypass: the modal's confirm button fires on tap when a screen
reader is on (same pattern as `useHoldToConfirm`).

## Threat-model matrix

| # | Attack vector | Threat actor | Impact | Mitigation in M1.1 | Residual risk | v2 escalation |
|---|---|---|---|---|---|---|
| 1 | Redlining via biased felt-unsafe cluster | Coordinated group with N devices | Routes pushed away from targeted neighborhood; structural harm | Apple Sign-in required + 3/24h+1-per-cluster rate limit + soft-cap → OTP gate at 5/24h; moderation queue surfaces clusters via "nearby reports" panel | Determined actor with N real Apple IDs + phones | App Attest (DeviceCheck); per-region trust scoring; advisory-board review for high-impact regions |
| 2 | Brigade-from-one-laptop (many anon-ids, one device) | Single attacker scripting submissions | Same as #1 at lower cost | Device-UUID in Keychain (survives anon-id rotation) + server IP-fingerprint log; alert when `device_uuid_count ≥ 5` on same IP / 24h | Attacker with VPN + multiple physical devices | Add per-IP request signing; rate-limit by `/24` subnet in addition to device |
| 3 | False place-report (e.g. "this restaurant is Black-owned") | Single bad actor | Reputational harm to a business | Anonymous + 8/24h rate limit + cross-check against `google_place_id` (sanity signal); flag → moderator review | Slow drip below rate-limit threshold | Add `place_attestation` step (e.g. require linked Google review or self-claim by business) |
| 4 | Flag brigading (auto-hide legitimate report via N false flags) | Group with multiple signed-in identities | Legitimate reports disappear before moderator can review | 2-flag auto-hide threshold requires 2 distinct IPs AND 2 distinct device-UUIDs (anti-brigade rule); same-IP/device flags queue for review instead | Group with 2+ real devices on 2+ real networks | Increase distinct-IP/device threshold; weight flags by flagger trust tier |
| 5 | Submitter content revision after flagging | Submitter caught with bad-faith report | Edit content to dodge the flag (e.g. flagged "racist accusation" → edited to "good restaurant") | UPDATE blocked except `{submitted_by, photo_uri}` allow-list; trigger enforces immutability of content/state columns | Submitter can DELETE + repost (loses original `id`, history) | If pattern emerges: add `delete_resubmit_cooldown` per device |
| 6 | Submitter hard-deletes to evade moderation | Submitter erasing trail | Audit history gone; brigade pattern unobservable | DELETE blocked at table level; `submitter_delete_report` RPC is soft-delete only (writes `removed_at`, row + IP + device_uuid survive for moderator review) | Submitter sees their report disappear from map (intended) but can't actually purge it | None — the soft-delete model is structurally adequate |
| 7 | Moderator-as-attacker (rogue mod removes inconvenient reports) | Compromised moderator account / future advisory-board member | Quiet suppression of legitimate reports affecting a target group | All moderation actions logged to `moderation_actions` with `actor_user_id`; UPDATE/DELETE on audit log blocked even for moderators (Postgres-enforced) | Discovery requires someone running an audit query; no live alerting | Build a "moderator activity" alert when any single moderator's removal rate spikes |
| 8 | Submitter PII exfiltration via SELECT | Any reader | Expose `submitted_by`, `submitter_ip`, `device_uuid` of condition reporters | RLS revokes direct table access; public view strips server-only columns; per-category anonymity filter strips `submitted_by` for condition reports even if a misbehaving client tried to write a name | Determined attacker tries SQL-injection at proxy level (no proxy in M1.1; direct Supabase REST) | If proxy added later: parameterize all queries; never interpolate user input into RLS predicates |
| 9 | Moderator PII exfiltration | Any reader | Identify who the moderators are (enables social-engineering / coordinated reporting against them) | `user_roles` SELECT moderator-only; menu entry render-gated; route obscurity is decorative (RLS is the actual security) | App binary reverse-engineering could leak the existence of `/moderation` route, but not the moderator identities | None — the RLS gate is structurally adequate |
| 10 | Notification-based denial-of-service | Brigade flagging many reports to spam moderator's push | Moderator's phone unusable; moderator stops responding | Per-report 30-min debounce on notifications; per-day cap of N notifications per moderator (TBD: 50?) | Brigade across many different reports defeats per-report debounce | Add cross-report rate-limit on notifications |
| 11 | Long-tail IP-history exposure | DB compromise (Supabase incident) | Old IPs disclosed | 90-day retention; `purge_old_ips` nightly cron NULLs `submitter_ip` and `flagger_ip` past threshold | Within-90-day window still exposed | Reduce retention to 30 days; consider IP hashing trade-off |
| 12 | Aggregate-view re-identification | Analyst correlating `moderation_actions_public` with other public signals | Identify a moderator's daily pattern from action timings | View pre-aggregates to `date_trunc('day')`; no actor or target IDs | Coarse pattern still visible (e.g. "moderation activity on Sundays") | Round counts to nearest 5 if/when scale demands; further-aggregate |

  abnormally.

## Operational checklist

### Standing up Supabase

1. **Create Supabase project.** Region: closest to expected user base
   (US-East for Brooklyn pilot). Note the project URL and `anon` key.
2. **Apply the migration.** Paste `supabase/migrations/0001_m1.1_initial.sql`
   into the Supabase SQL editor and run.
3. **Bootstrap your moderator role.** Sign in with Apple in the Fresh Greens
   app to create your `auth.users` row. Note your `auth.uid()` (visible in
   the Supabase dashboard under Authentication → Users). Edit
   `supabase/seed.sql` to replace the placeholder UUID, then run it via the
   SQL editor.
4. **Enable `pg_cron` and schedule the IP-retention job.** Supabase →
   Database → Extensions → enable `pg_cron`. Run the
   `SELECT cron.schedule(...)` line from the migration.
5. **Configure Apple Sign-in.** Supabase → Authentication → Providers →
   Apple → enable, configure your Apple Developer credentials.
6. **Configure phone OTP.** Supabase → Authentication → Providers → Phone →
   enable, configure SMS backend (start with Twilio sandbox for testing,
   real Twilio for ship).
7. **Set env vars in the Fresh Greens build.** `.env.local`:
   ```
   EXPO_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
   EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon key>
   ```
8. **Deploy the notification Edge Function.** Supabase CLI:
   `supabase functions deploy notify-moderator`.
9. **Two-device verification test.** Sign in on two phones; submit a report
   from one; verify it appears on the other within ~5 seconds.
10. **Deploy the moderation-aggregate static page.** Single HTML file on the
    portfolio domain that fetches the public Edge Function endpoint. Link
    from the case study.

### Definition of done for M1.1

- All four checks above pass: two devices see each other's reports, condition
  submissions require Apple Sign-in, the moderator queue receives a push when
  a report is flagged, the aggregate-transparency page renders live counts.
- Threat-model matrix rows 1–12 each have a verifiable mitigation in code or
  config (no "TODO" rows).
- `docs/learnings.md` entry written for the build session.
