## Anti-Patterns Verdict

**Clean. No AI slop detected.**

Code is notably free of anti-patterns named in PRODUCT.md's anti-references. No gradient text, glassmorphism, or decorative fills. No eyebrow label on every section. No aggressive conversion CTAs or alarm-register language — except the isolated "Heads up!" discussed under H8. Reserved colors used exclusively where the rulebook permits: orange on hazard chips, fadedgreen/burntgreen on safe chips and all-clear, freshgreen on primary CTAs only. The `Star` icon in trusted-station row uses `burntgreen` — correct (yellow carve-out applies only to explicit "saved/favorite" toggle in `PreferredStar`). `RouteAllClearChip` is non-interactive (`View` not `Pressable`) — semantically correct.

## Cognitive Load

**Browse mode (no destination): Low-to-moderate.** Sheet's collapsed-by-default recommendation section is the right call. Map immediately usable and legible. Eyebrow/neighborhood/weather header stack three distinct pieces but visually compact and serve different temporal questions. Sticky category chips add a fourth layer but well-placed. "Show all categories" progressive disclosure appropriate.

**Route-preview mode (destination set): Moderate.** Card presents 9–11 distinct information atoms before user can press Go. Each atom is justified, but density is high for a decision in a charged moment. Type-size ladder (34/15/13/12pt) does significant work to triage. Risk: in-car or time-pressured use could overwhelm a user who hasn't internalized the card's vocabulary. Route-cycle chevrons + "N of M" add one more parsing task when multiple routes exist.

**Detail card layer (RouteHazardDetailCard): Low.** Two-paragraph body, destination breadcrumb, pager row are well-structured. The "Manage in Zone Preferences →" link gives an exit that doesn't feel like a trap.

## Emotional Journey

**Cold start → browse mode:** Map opens to quiet basemap; community pins load. Browse sheet's collapsed state gives user a moment to read the map. Map-coach overlay informative without being alarmist. Word "community" in first thing user reads ("Built on community knowledge") anchors brand register. *Grounded, curious.*

**Search → route established:** Route line appears, ETA card loads with haptic. "Safest route with current conditions." is calm, assertive. Daylight strip quietly contextualizes the trip's light envelope. *Reassured, ready.*

**Hazard chips load:** "Along this route: 1 police zone" in briefing register, not alarm. Orange WarningDiamond contained by chip's rounded pill — reads as data, not danger. Safe chips alongside hazards shift tone from "brace for it" toward "here's the full picture." *Informed, not frightened.*

**Charged moment (Black driver considering route with police zones):** App surfaces police-zone data without editorial embellishment. Chip says "1 police zone," detail card gives data source and how it affects scoring, offers "Manage in Zone Preferences" — agency without alarm. Destination breadcrumb keeps spatial context intact. The thesis's core moment, design handles it composedly. *Acknowledged, in control.*

**Errors / no-route state:** No-route PathIcon + "No route available" avoids generic gray EmptyState card. Wiltedgreen headline matches card's vocabulary. Escape immediately above. *Matter-of-fact, not abandoned.*

Hazard chip / all-clear chip / safe chip palette reads as a coherent binary language without leaking into decorative use. Star in trusted-station row uses burntgreen, correctly avoiding the yellow-only-for-saved-favorite exception.

**2. Route-preview card's type ladder earns its density.** 34pt ETA → 15pt arrival → 13pt via+conditions → 12pt chips compresses trip data into scannable vertical. `largeTitleEmphasized` ETA dominant enough that a time-pressured user can grasp the single most important number and decide without reading the rest. Entrance haptic + fade on first reveal gives ETA moment real weight.

## Priority Issues

**[P1] Route hazard chips have no tap affordance**
- What: `RouteWarningChip` and `RouteSafeChip` are `Pressable` — tapping focuses the map on the first matching hazard. But chips render as static pills with no interactive cue: no chevron, no underline, no press-state change beyond `pressedDim`.
- Why it matters: Thesis's core claim ("the UI shows its work") requires users to actually investigate hazard locations. If no one discovers chip is tappable, the spatial drill-down is a dead feature for sighted users. VoiceOver gets "Show 1 police zone on map" — AT users better served than sighted ones, an inversion of the usual pattern.
- Fix: Add trailing `>` or small `CaretRight` icon inside each `RouteWarningChip` and `RouteSafeChip` at 16pt size. Aligns with destination breadcrumb pattern in `RouteHazardDetailCard`.

**[P1] "Heads up!" exclamation breaks the Steady Companion register**
- What: Suggested-departure row renders: `"Heads up! You can leave in a bit and still make it on time with some added daylight on your route."` Only instance of alarm-register punctuation in entire route-preview card.
- Why it matters: PRODUCT.md names "alarmist safety-app" as direct anti-reference. `.cursorrules` register guidance ("calm, trustworthy, grounded") applies to copy as much as color. "Heads up!" is verbal equivalent of a notification badge.
- Fix: Rewrite to: `"You can leave a little later and still arrive with more daylight on this route."` Preserves suggestion, removes exclamation.

**[P2] No-destination GPS wait state is invisible to sighted users**
- What: Recenter FAB renders immediately with no visual change between "GPS ready" and "GPS acquiring." `accessibilityLabel` correctly says "waiting for location" for VoiceOver, but nothing on screen communicates to sighted users.
- Why it matters: Sighted user who taps Recenter before GPS ready sees nothing happen, no model of why. In browse mode 1-3 seconds; in degraded GPS, could persist.
- Fix: Add small `ActivityIndicator` or pulsing animation inside FAB's glyph slot when `!userLocation`, replacing `SidebtnRecenter`. Apple Maps pattern. Existing `reduceMotion` guard can suppress.

**[P2] Map coach is permanently unrecoverable after first dismissal**
- What: `useCoachMark('home-map-intro')` shows overlay once, marks dismissed on "Got it" tap. No second path to view explanation — no "?" help button, no long-press affordance, no entry in /menu.
- Why it matters: Users dismiss first-launch overlays without reading (the "I'll figure it out" pattern). Only in-app explanation of what zones, community pins, edge indicators mean then permanently gone.
- Fix: Add "Map guide" row to /menu's settings list. Tap re-displays coach card. Two-line change.

**[P3] "Community flag" chip label is domain-opaque**
- What: `ROUTE_HAZARD_LABEL` for `community` renders as "1 community flag." Internal vocabulary — report flow says "report" everywhere, map coach says "flags."
- Why it matters: Heuristic #2 (match user's mental model). "Flag" implies a moderation action in most app contexts, not a community safety signal.
- Fix: Rename to `['community report', 'community reports']` in `ROUTE_HAZARD_LABEL`.

**[P3] Placement-mode hint text is subtly contradictory**
- What: Placement bar instruction: `"Tap the map to move the pin. Drag to move around."` "Drag to move around" describes panning the map (natural gesture), not dragging the pin. PR history confirms drag-the-pin was attempted and reverted; "Drag to move around" is a vestige.
- Why it matters: A user who reads literally will try to drag the pin and find it doesn't move.
- Fix: Simplify to: `"Tap anywhere on the map to move the pin."`

## Persona Red Flags

**Sam (accessibility — VoiceOver user):**
The screen is unusually well-prepared for VoiceOver. Notable strengths: `routeHazardChips` row has combined `accessibilityLabel` reading all hazard + safe chips as single sentence; `RouteAllClearChip` hidden from AT (status not action — correct); route cycling chevrons have `accessibilityState` and labels including "Previous/Next route." Main gap: map coach overlay (`accessibilityRole="button"` on scrim Pressable) read as single button — title and body copy unreachable as distinct elements. Sam hears "Dismiss map guide" and nothing about what the guide says.

**Casey (distracted mobile — one-handed, glancing):**
Route-preview card demands more visual parsing than a glance allows. ETA legible at a glance. Hazard chip row requires second look to distinguish loading/failed/hazards/all-clear states — three chip variants look similar at peripheral vision. Casey unlikely to discover chip-tap drill-down and will treat chip row as read-only status strip. "Heads up!" copy most likely element to catch Casey's eye mid-scroll — exactly the wrong moment to introduce alarm register.

**Black driver assessing safety in a charged moment:**
App handles this moment with composure. "Along this route: 1 police zone" briefing is calm. Tap chip → `focusRouteHazardAtIndex` → map zoom → `RouteHazardDetailCard` delivers two-paragraph data explanation that does not editorialize. Destination breadcrumb ("Back to [destination]") keeps spatial context intact through drill-down. App does not use red, does not say "danger," does not add haptics beyond `selectionAsync()`. Thesis's most important moment; design earns it.

One unresolved risk: if route-check fails, gray "Couldn't check route · Retry" chip shows in place of hazard data. A driver who taps Retry but gets second failure has no fallback. Architectural constraint, not design failure, but copy could acknowledge uncertainty more explicitly: "Route check unavailable — drive with extra care" would give this user more to act on.

## Minor Observations

- `dragHandleArea` in browse mode `paddingVertical: 16` makes touchable ~36pt — below 44pt painted target rule. `DragHandle` glyph is 4pt. Same issue prior critique surfaced at P2.
- `routeZonesLoadingChip` `paddingVertical: 8` (~28pt tall) while `routeZonesRetryChip` `minHeight: 44`. Loading chip not interactive so tap rule doesn't apply, but visual inconsistency between two chip heights in same slot is minor jitter.
- `mapCoachCard` max-width hardcoded at `320`; equivalent constraint in `HomeBrowseSheet` uses spacing tokens. Inconsistency low-stakes for a one-off overlay.
- "trustedOnRouteRow" star is `colors.burntgreen` rather than yellow used by `PreferredStar`. Correct per reserved-color rule (yellow carve-out is for explicit saved/favorite toggle).
- `WeatherDrivingCard` error state shows "—°" even though retry path is available. User who has never seen weather card working could interpret dash as "no data" rather than "tap to retry." Consider adding small retry icon (e.g., `ArrowClockwise`) matching `RouteZonesFetchFailedChip` pattern.

## Questions to Consider

- When should the map coach be re-triggerable? A "Map guide" menu entry is the minimal path; a more discoverable variant would be a persistent `?` chip somewhere on the map chrome — but risks clutter on an already-layered screen.
- Is "community report" the right chip label? Aligns with "Trusted by your community" language in browse sheet. Worth resolving copy-level before label propagates further.
- How does the route-preview card handle very long destination names? `numberOfLines={1}` on `routeDestTitle` with `flex: 1` clips long names; test on iPhone SE (320pt width) with bookmark visible.
- Should the "Suggested departure" chip be time-aware? Currently captured at first render; user who waits sees stale chip pointing to past time. Reactive `past-time` Alert handles confirmation error, but chip could be eliminated proactively by re-running `suggestedDepartureForDaylight` on minute-resolution tick.
- What does the placement-bar's drag handle communicate? Decorative (no swipe gesture). DragHandle visual convention universally signals "you can swipe this." Removing the drag handle from placement mode would reduce false affordance.
